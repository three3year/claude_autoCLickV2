# ADR 0004：視窗先開、引擎背景載入，範本改為執行前預載

Status: accepted（2026-08-16）

## 背景

打包版從點擊 exe 到主視窗可操作，熱啟動實測 3–4 秒、乾淨環境冷啟動歷史紀錄
15.3 秒，且開窗前全黑無任何回饋。量測與程式碼調查確認成本依序為：

1. `App.__init__` 一開始就同步建 `Engine()`——`import torch` + 反序列化
   84MB DINOv2 權重，全部做完主視窗才第一次映射（最大單項）。
2. `load_profile` 對 profile 內全部範本（現況 87 個）逐一 `load_or_register`：
   每個算 SHA-1、讀 3–4 個檔，每次啟動都做。
3. spec 開了 `upx=True`，366MB 的 torch DLL 群每次載入都要先解壓。

打包已是 onedir（ADR 0002 時代拍板，onefile 4.6s vs onedir 1.4s），
發佈形式不是本輪的問題。

## 決策

驗收標準定為「主視窗出現＋按鈕能按 < 3 秒（熱啟動）」，據此：

1. **視窗先開，引擎背景載入**：主視窗建好即進 mainloop，torch/DINOv2 在
   背景執行緒載入。「視窗可操作」與「引擎就緒」自此是兩個時間點
   （詞彙見 app/GLOSSARY.md「啟動與就緒」）。不加 splash。
2. **引擎就緒前的辨識類操作一律 modal 對話框提示並拒絕**（含 F12 熱鍵、
   主視窗執行鈕），使用者稍後自行重試——不排隊自動開始、不置灰按鈕。
   背景載入失敗維持現行為：modal 警告後降級 coarse-only。
   編輯流程、範本管理等不需辨識的操作不受影響。
3. **範本改為執行前預載**：應用啟動不再 `load_profile` 全庫登錄；按下執行後、
   流程開跑前，一次掃描載入該流程引用的全部範本（不是逐步驟才載），
   執行視窗顯示「準備範本中…」。單一範本的辨識操作（比對測試、即時找圖）
   在使用當下載那一張。
4. **關閉 UPX**：dist 由約 700MB 變大至約 900MB–1GB，換每次啟動
   （尤其冷啟動）省下解壓成本，打包也更快。

## 取捨

- **背景載入 vs 同步＋splash**：splash 只是遮住等待，冷啟動仍可能 10 秒以上
  才能操作；背景載入直接把可操作時間縮到 tkinter 起來為止。代價是引入
  「就緒前」狀態，所有辨識入口都要多一道就緒檢查。
- **拒絕 vs 排隊自動開始**：就緒前按執行改為明確拒絕——行為單純直白，
  不需要可取消的排隊機制；代價是使用者要自己重按一次。
- **執行前預載 vs 啟動全載 vs 逐步驟懶載**：啟動全載付 87 次檔案讀取在
  開窗路徑上；逐步驟懶載會讓執行中每一拍的即時性不可預期。整份流程一次
  預載把成本集中在按下執行後的一小段（熱快取下預估一秒內），且有明確的
  「準備範本中」回饋。
- **關 UPX 換磁碟空間**：啟動速度優先於幾百 MB 硬碟占用。

## 影響

- 推翻 app/CLAUDE.md 記載的「app 啟動建立一次 Engine、`load_profile`
  自動登錄」契約；`ensure_registered()` 的語意改由執行前預載承接，
  實作時需同步改寫該檔。
- 任何新增的辨識入口都必須先過「引擎就緒」檢查，否則會在就緒前炸出
  未定義行為。

## 後記（2026-10-05）

第 3 點「執行視窗顯示『準備範本中…』」的顯示文字已被
`.scratch/start-delay-floor/spec.md` 取代：預載改在`開始延遲`的倒數中進行，
狀態字顯示「倒數啟動中…」／「等待準備範本完成…」，「準備範本中…（N 張）」只留在
執行紀錄。預載的時機（按下執行後、開跑前一次載齊）不變。

## 後記（2026-10-10）

第 3 點的預載時機將在格式階段（ADR 0014）改掉：**讀取流程時就在背景預載**（引擎未就緒則就緒後開始），
按執行時只補缺的、背景那份沒完就接著等。原因：實測讀取流程會清掉登錄產物，讀取後第一次執行要現場登錄
82 張約 7.5 秒；已快取時從磁碟讀約 2.6 秒，藏在開始延遲裡。驗證模型不另外暖機（首次推論成本 <0.2 秒）。
細節見 `.scratch/project-cleanup/issues/03-diagnose-post-preload-wait.md`。
