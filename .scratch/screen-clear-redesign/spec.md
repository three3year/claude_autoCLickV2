# Spec: 清場還原重設計——驗證式還原、modal 堆疊與保險絲

Status: implemented (2026-08-16；ADR 0003；打包版互動冒煙輪見 issues/08 Comments)

## Problem Statement

拾取（框選新增範本圖等）結束後，步驟編輯對話框偶發不重新顯示：畫面上只剩
主視窗、但主視窗被 modal grab 擋住點不到；按 Esc 能關掉看不見的對話框，
證實子視窗活著、握著鍵盤 grab，只是沒被畫出來。發生後往往「一直壞」，
使用者只能重開程式，剛截的圖也跟著遺失。打包版實際使用中回報，雙螢幕環境。

調查確認為`清場`（`ui_overlay.screen_clear`）還原流程的結構缺陷，非單一 bug：

1. **隱藏有保護、還原沒有**：進場有 `update()` + 0.1s 等待確保隱藏生效；
   離場 `deiconify()` 只是把 map 請求排進佇列就繼續往下走，接著 overlay
   被銷毀、前景讓給背後的應用程式，map 可能未完成（ui_overlay.py:215-242）。
2. **對話框從未被 lift**：還原後只 `root.lift()`；子視窗只有在 grab 快照
   正確時才拿到 `focus_force()`，而找圖對話框是全 app Combobox 最多的視窗，
   `safe_grab_current()` 回 `None` 的機率最高（ui_overlay.py:236-242）。
3. **壞一次就一直壞**：還原對象由 `state()` 快照篩選，withdrawn 視為
   「刻意隱藏」永遠跳過——任何一次還原失手，之後每次清場都不再還原它
   （ui_overlay.py:193-195）。
4. **modal 靠輪詢協商**：沒有 modal 堆疊，各視窗各跑「100ms × 15 次逾時
   放棄」的 `after` 迴圈互搶 grab；存圖後同步整庫重登錄（`reload_profile`
   + `refresh_templates`）卡住主執行緒數秒即燒光重試預算，對話框回來也
   不再 modal（ui_overlay.py:119-150、app.py:1404-1405）。
5. **例外不可見**：未攔截例外只寫進主視窗紀錄面板；主視窗正隱藏時使用者
   完全看不到（app.py:2020-2028）。

## Solution

重新設計清場的還原與 modal 管理，四道防線：

1. **驗證式還原**：離場與進場對稱——照清單逐一 `deiconify`，以 map 事件
   確認每個視窗真的畫出來（逾時重試），每個還原的視窗都 lift，全部確認
   可見、grab 交還完成後才銷毀 overlay。
2. **記住自己隱藏的**：清場明確記錄「本次 withdraw 的視窗清單」（含 zoomed
   快照），離場照清單全數還原，不再以 `state()` 猜測——根除黏著失敗。
3. **明確 modal 堆疊**：全域一個堆疊，開 modal 入堆、關閉出堆，grab 永遠
   歸堆頂；以事件驅動（堆頂變更、堆頂視窗 `<Map>`）取代輪詢逾時放棄。
4. **全域保險絲＋檔案日誌**：低頻監控「grab 持有者不可見」，超過門檻自動
   救回並記日誌；清場進出、還原驗證、grab 轉移、保險絲觸發、未攔截例外
   全部落地到日誌檔，偶發問題事後可查證。

存圖後的整庫重登錄延後到「子視窗已確認可見」之後執行，視窗先回來再短暫卡。

## User Stories

1. 身為使用者，我想在框選完成後子視窗每一次都確實回到畫面上，讓新增範本圖不再偶發卡死。
2. 身為使用者，我想在框選取消（Esc）時視窗同樣確實還原，讓取消與完成一樣安全。
3. 身為使用者，我想在還原偶發失手時程式自動重試到視窗真的畫出來，而不是繼續往下走假裝成功。
4. 身為使用者，我想讓某一次還原失敗不影響下一次清場（不再「壞一次就一直壞」），讓偶發問題不升級成永久問題。
5. 身為使用者，我想在存圖後先看到對話框回來、整庫重登錄再接著跑，讓「視窗消失」與「程式卡住」兩種感受分開。
6. 身為使用者，我想在多個子視窗疊開（編輯對話框＋比對測試結果等）時，grab 永遠在最上層的視窗手上，讓每一層都點得到該點的東西。
7. 身為使用者，我想在關掉上層視窗後 grab 確實回到下層，讓巢狀對話框的操作順序不會卡住。
8. 身為使用者，我想在萬一仍發生「握有 grab 的視窗不可見」時，程式在幾秒內自動把它救回畫面，讓我不必重開程式。
9. 身為使用者，我想在問題發生時有日誌檔可以拿去回報（清場進出、還原重試、保險絲觸發、例外），讓偶發問題不需要重現也能查。
10. 身為使用者，我想在雙螢幕環境下以上行為一樣可靠，讓螢幕配置不影響穩定性。
11. 身為使用者，我想讓執行流程用的迷你視窗顯隱（刻意隱藏的視窗）不被清場還原誤觸，讓兩套顯隱機制互不干擾。

## Implementation Decisions

- **改動集中**：`ui_overlay.py`（`screen_clear`、`_regrab`、`pick`）、
  `ui_dialogs.py`（`make_modal`）、`app.py`（`save_captured` 延後重登錄、
  保險絲、例外落地）。清場對外介面（context manager、可巢狀）不變，
  呼叫端原則上不動。
- **驗證式還原**：離場時逐視窗 `deiconify`（zoomed 依快照 `state("zoomed")`）
  → 等 `<Map>`／`winfo_viewable()` 確認（事件驅動＋逾時重試，重試次數與
  間隔記日誌）→ 每個視窗 lift（root 先、對話框後，維持 Z 序）→ 全部可見
  後把 grab 交還堆頂 → 最後才讓 `pick()` 銷毀 overlay。「還原全程在覆蓋層
  後面完成、一次揭示」的既有拍板保留（app/CLAUDE.md 踩坑紀錄）。
- **還原清單**：`screen_clear.__enter__` 記錄本次實際 withdraw 的視窗與其
  wm state 快照；`__exit__` 照清單還原。視窗已被銷毀的（`winfo_exists()`
  為假）跳過並記日誌。不在清單上的視窗一律不碰——執行流程的迷你視窗
  顯隱（app.py 的 withdraw/deiconify）自然隔離。
- **modal 堆疊**：模組層級單一堆疊；`make_modal` 入堆、`<Destroy>` 出堆
  （含中途出堆——非堆頂視窗被關閉時直接從堆中移除）；grab 一律歸堆頂，
  堆頂變更或堆頂視窗 `<Map>` 時奪回。`_regrab` 的「15 次放棄」與
  `takeover` 白名單協商廢除，`show_match_test` 的 `prev` 參數由堆疊語意
  自然取代。Combobox popdown 的暫時 grab（`safe_grab_current` 回 `None`
  的情境）視為過客：不入堆、popdown 關閉後堆頂奪回。
- **清場與堆疊整合**：清場期間堆疊暫停奪 grab（overlay 持有 grab 是拾取
  的必要條件，`_guard_grab` 保留）；離場還原完成後 grab 歸堆頂。
- **重登錄延後**：`save_captured` 不再同步呼叫 `reload_profile` +
  `refresh_templates`，改排入「清場還原完成（視窗確認可見）之後」的
  `after()` 佇列。延後期間新範本尚未登錄進引擎——期間觸發的比對測試等
  引擎查詢必須先等重登錄完成（實作票處理排序，如以旗標／佇列串接），
  不得對新範本名 KeyError。
- **保險絲**：root 低頻（秒級）檢查 grab 持有者 `winfo_viewable()`；
  連續不可見超過門檻（數秒）且不在清場中 → 自動 `deiconify` + lift +
  `focus_force` 並記日誌。正常運作時保險絲永不觸發；觸發即代表機制有洞，
  日誌是修洞的證據。
- **檔案日誌**：輕量檔案日誌（exe／repo 旁固定位置，大小上限或輪替從簡），
  記錄：清場進出場與視窗清單、每視窗還原驗證結果與重試數、grab 轉移與
  堆疊變化、保險絲觸發、未攔截例外（`report_callback_exception` 除寫入
  紀錄面板外一併落地）。
- **清場中不彈隱形對話框**：清場期間不得以已隱藏的視窗為 parent 彈
  messagebox（現行 click/drag 拾取的 `_region_origin` 有此問題）——改為
  清場結束後再彈，或以可見視窗為 parent。
- 立 ADR 一篇：modal 堆疊取代輪詢協商＋驗證式還原（難回頭、日後會被問
  「為什麼」、有真取捨：Tk 層對稱驗證 vs win32 API 直接控制，拍板前者）。
- 詞彙表已更新（app/CONTEXT.md 新增「拾取」「清場」條目）。
- 收尾照慣例重新打包（`app\build.bat`），使用者用的是打包版。

## Testing Decisions

- **唯一新增的測試接縫**：「modal 堆疊＋清場還原清單」共用一個純狀態機
  （入堆/出堆/中途移除/誰該持有 grab/該還原誰與其順序/驗證失敗是否重試），
  決策邏輯與 Tk 呼叫完全分離、Tk 側只是薄執行層，純 pytest 覆蓋。
  只測外部行為：給定事件序列（開窗/關窗/清場進出/map 確認/逾時），驗
  「此刻誰該持有 grab、該還原誰」，不驗內部呼叫順序。
- **grab/modal 的實際行為**：`event_generate` 合成事件繞過 grab 路由
  （app/CLAUDE.md 既有紀錄），驗證「點擊被 grab 導走／救回」必須用真實
  輸入（`win.click` SendInput）——僅做少量煙霧驗證，不建整套 GUI 測試。
- **清場還原整合**：以既有 GUI 測試手法（`after()` 排程互動、PrintWindow
  截圖）驗證「隱藏→還原→視窗可見」一輪；偶發時序問題主要靠檔案日誌
  在真實使用中蒐證，不追求在測試中重現。
- 修改 runner 之外的 UI 機制，既有 pytest 回歸網（runner／profile／flowpack）
  必須全綠——證明清場介面不變、呼叫端未被波及。

## Out of Scope

- Esc 逃生後截圖遺失的暫存／找回機制——還原修好後該情境自然消失（拍板不做）。
- 整庫重登錄搬背景執行緒（引擎物件的執行緒安全未釐清，風險大；延後執行已
  解決「視窗消失」的部分，卡頓本身留待日後）。
- 以 win32 API（SetForegroundWindow/ShowWindow）直接控制視窗——拍板走
  Tk 層驗證式還原，win32 僅既有用途不擴大。
- 每存一張圖就整庫重登錄的成本優化（增量登錄）。
- 並行執行相關互動（本輪未移植）。
