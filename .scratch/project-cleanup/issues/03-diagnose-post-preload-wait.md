# 診斷「預載完還再等 3 秒」

Type: task
Status: resolved

## Question

使用者觀察：按下執行後，範本預載印出「範本就緒」之後還要再等約 3 秒才開始。執行器程式碼
（`app/automation/runner.py` 的 `start`／`_run`／`_preload`）是下限語意：`due = 按下時間＋3 秒`，預載後只睡剩餘時間。
推測是開頭校準的第一次引擎查詢觸發 DINOv2 模型暖機（CPU 上第一次推論要數秒）。

要做的（HITL：需要遊戲畫面在、使用者在場）：
- 在預載結束、`_sleep` 前後、`_calibrate` 內第一次 `query` 前後加帶時間戳的檔案日誌（臨時，不進 commit），
  用打包版或 repo 版實跑一次四份流程之一的開頭。
- 記下每段耗時：預載、剩餘睡眠、校準第一次查詢、校準第二次查詢。

Answer 要寫：多出來的時間在哪一段、量到幾秒；若是模型暖機，暖機要在預載階段做（一次假查詢）還是在引擎就緒時做
（app 啟動背景載入模型後立刻暖機）——這是霧區「模型暖機實作方式」切票的依據。

## Answer

（2026-10-10，離線實測；不需遊戲在場——用真的 Runner＋真的引擎，`_grab` 換成 add4.mp4 一格繁中最大化畫面，
打包版 `早_繁中` 工作區的複本，計時腳本在 session scratchpad，未進 repo）

**不是模型暖機。「範本就緒」之後那 3 秒就是開始延遲本身。** 按下執行後的時間軸（同一個 session 第二次以後執行）：

| 時間點 | 事件 |
|---|---|
| +0.000s | 3 秒後開始執行／準備範本中…（5 張） |
| +0.006s | 範本就緒（登錄產物已在記憶體，預載幾乎不花時間） |
| +3.0s | 開始延遲到期 |
| +3.48s | 開頭校準完成、開始第一步 |

各段耗時：
- **預載**：整份流程 82 張——未登錄（剛開流程／工作區重建）7.5 秒；登錄產物在磁碟、app 剛啟動 2.6 秒；
  同一 session 已載過 0 秒。所以「預載完再等滿 3 秒」只發生在同一 session 第二次以後的執行；那時整段延遲都排在「範本就緒」之後。
- **剩餘睡眠**：3 秒減預載耗時，照設計。
- **校準第一次與第二次查詢**：標題列圖示 0.33–0.41 秒、標題列關閉鈕 0.37–0.40 秒（全尺度粗篩為主）；
  第一次跟之後幾次一樣快。DINOv2 第一次 embed 0.06 秒，跟之後相同；唯一看到首次成本的是登錄時第一張 0.22 秒對之後 0.075 秒，約 0.15 秒。
  主對找不到改用備用對時，最多查 4 次，約 1.5 秒。

結論：
- 暖機不做（預載或引擎就緒時都不做）：要省的時間不到 0.2 秒。地圖霧區「模型暖機實作方式」清掉。

  讀取後第一次執行要現場登錄全部範本（82 張 7.5 秒），第一步約在按下後 8 秒才開始。
  **使用者決定（2026-10-10，grilling）：預載改在讀取流程時於背景進行，併進格式階段；階段 0 取消。**

  2. 還沒載完就按執行：接著等同一份，3 秒開始延遲仍從按下起算（現行「等待準備範本完成」）。

附帶發現（不在本地圖範圍）：`torch.hub.load("facebookresearch/dinov2", …)` 沒指定分支，每次載入都會連
`github.com/…/tree/main/` 判斷分支。斷網（URLError）會退回本機快取，**但 GitHub 回 5xx（實測遇到 504）會直接拋錯**，
引擎**降成只用粗篩**（`coarse_only=True`；app 會跳警告，但原因是 GitHub 一時出錯，不是本機壞了）。打包版也走同一條路。修法候選：repo 字串寫成
`facebookresearch/dinov2:main`，或用 `source="local"` 指向 hub 快取目錄。交由使用者決定另外修。
→ 使用者要修：已改成 `:main`（`src/subject_detection/verification.py`），模擬 GitHub 一律 504 時載入成功且零網路呼叫；引擎測試 66 過。
