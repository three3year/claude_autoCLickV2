# Spec：影片轉流程規則＋agent 文件階段

Status: ready-for-agent

專案整理地圖的第 2 階段（[階段切法與順序](../project-cleanup/issues/01-phases-and-order.md)）。前置票：[影片轉流程產固定矩形與忙碌檢查的規則](../project-cleanup/issues/04-v2f-fixed-rect-and-busy-check-rules.md)（下稱「04」）、[agent 文件結構](../project-cleanup/issues/10-agent-docs-structure.md)（下稱「10」）、[補充流程規則](../project-cleanup/issues/13-supplement-flow-rules.md)（下稱「13」）；flow.yaml 鍵名與預設見 [flow.yaml 具體 schema](../project-cleanup/issues/02-flow-yaml-schema.md)。決策正本另有 ADR 0009（流程尺度）、0012（座標基準點）、0013（支援倍率範圍與拾取檢查）、0014（流程＝資料夾、步驟選項裁減）。詞彙以 `app/CONTEXT.md` 為準（`補充`、`影片倍率`、`交付報告`、`待重拍` 已是目標狀態）。

## 需要你決定的

### 交付報告拆檔時，檔名怎麼取、沒被區段包住的步驟歸哪份？

決定（2026-10-11）：(a) 區段開頭找圖的範本名；區段之間的零散頂層步驟併成一份，用那段第一個找圖的範本命名。

13 規則 11 定了「總覽＋每個頂層區段一份」，留給 spec 的是檔名與零散步驟。報告裡用內容指稱步驟、不寫死編號（補充插入後編號會位移），檔名也一樣不能用編號。

- (a) 一個頂層區段一份，檔名取區段開頭找圖的範本名（例 `分岔-公告关闭.md`、`重複-标题_制造站.md`）；兩個區段之間連續的零散頂層步驟併成一份，用那段第一個找圖的範本命名（例 `步驟-基建入口.md`）；撞名加序號。總覽依流程順序列出各份的連結（建議）。代價：範本改名時檔名不會自動跟著改，要靠 edit-flow 順手改。
- (b) 零散步驟併進前一個區段那份。代價：檔名說的區段跟內容對不上，agent 照檔名找會漏。
- (c) 檔名用流程順序編號（`01.md`…）。代價：插入一段之後後面全部改名，違反「不寫死編號」。

### 四份在用流程的舊 `交付報告.md` 拆完後怎麼處理？

決定（2026-10-11）：(a) 新結構只寫現況，舊檔原樣搬成 `交付報告/舊紀錄.md` 保留。

舊報告每份約 200–450 行，大半是日期分節的修改歷史（例「2026-10-09：快速置入前先查 1–7 號線索」）。流程資料夾不在 git，刪掉就找不回來。

- (a) 新結構只寫現況（每個區段做什麼、為什麼、已知風險、待重拍、待確認），過期內容標出；舊檔原樣搬成 `交付報告/舊紀錄.md`，總覽註明「歷史，平常不必讀」（建議）。代價：資料夾裡留一份大檔，但 agent 有總覽指路就不會去讀。
- (b) 歷史逐節併進對應區段那份。代價：工作量大，而且違反「不在尾巴累積歷史」，之後每次補充都要決定歷史寫在哪。
- (c) 拆完刪掉舊檔。代價：修改理由（為什麼不用某張圖、哪些分數比過）永久遺失。

### 驗收 ② 用哪一支完整示範影片獨立重轉？

決定（2026-10-11）：(c) demo2（早_繁中）。

13 規則 13 的第二項：另挑一支轉過的完整示範影片，用 video-to-flow 獨立重轉，拾取檢查全過。

- (a) demo3（晚_繁中，46 秒、20fps 固定、5.2 Mbps）（建議）。代價：只有 26 張範本，涵蓋的情境較少；但驗收 ① 已經是簡中，這支補上繁中最大化。
- (b) demo4（晚_簡中，68 秒、變動幀率 13.6fps）。代價：跟驗收 ① 同一個客戶端；好處是順便驗證工具全程用順序讀幀。
- (c) demo2（早_繁中，164 秒、82 張範本）。代價：工作量大約是 demo3 的四倍，挑幀覆核要花很多輪。

### 補充在工具上做成什麼入口？

決定（2026-10-11）：獨立子指令 `insert <計畫> <流程資料夾>`，跟 `assemble` 共用量測與自我驗證；不做成 `assemble` 的模式。

### 測試接縫用哪幾個？

決定（2026-10-11）：四個——組裝（已有）、補充插入（新）、檢查指令（新）、格式規範對照（新）。三個 skill 不寫單元測試，靠階段驗收實跑（見 [Testing Decisions](<#Testing Decisions>)）。

## Problem Statement

流程多半是 agent 照使用者的示範影片轉出來的，但轉出來的東西還不能直接用，改流程的路也不通：

- 影片轉流程工具不產`固定矩形`、不支援`忙碌檢查`，計畫還用舊鍵名（`colorCheck`、`onNotFound`、毫秒）。每份新流程都要事後手動補框、補勾，四份在用流程的 331 個固定矩形全是手框的。
- 使用者常只錄一小段（例 add5.mp4 換班時找回收站），要插進既有流程。現在只能手寫一次性腳本（`add_recycle.py`），倍率、原點、插入點全靠人核對。影片錄的視窗大小也不一定跟建流程時一樣（早_繁中執行時是 ×0.886）。
- 只想改結構（加分岔、改 `on_fail`、搬步驟）時沒有 skill 可用，agent 不知道 flow.yaml 每個鍵的意思。執行語意散在 `app/CLAUDE.md`（給開發用的）、`plan-format.md`、`SKILL.md` 三處，有三處互相牴觸，agent 容易照錯的那份寫，或乾脆猜一個座標。
- `交付報告.md` 一份流程一個大檔，按日期往下累積修改歷史。之後的 agent 只想改其中一段，也得整份讀完。
- 手改 flow.yaml 之後，沒有不開 app 就能檢查的辦法；區段交錯、相對座標沒有原點、缺圖，都要到執行時才發現。

## Solution

一份格式規範、兩個入口 skill、一個共用的影片量測 skill，加上一個檢查指令：

- **`docs/flow-format.md`** 是 flow.yaml 唯一的正本：欄位、執行語意、常見寫法，給寫流程的 agent 看。pytest 把它的欄位表跟 app 的預設表與讀檔鍵對照，對不上就紅。
- **video-to-flow**：新流程的入口。影片 → 新的流程資料夾，直接帶固定矩形（框每邊外推 50%，捲動清單整條拉長）與計畫明寫的忙碌檢查；拾取檢查三項全做，「唯一」不過標待重拍。
- **edit-flow**：既有流程的入口。改結構與選項；要像素值時，能改成找圖就改成找圖，不能就請使用者錄一段，交給 video-measure 量完插進去；都不行就不寫那一步，列進交付清單。永遠不寫猜的座標。
- **video-measure**：影片特有的知識（錄影要求、掃描、游標與特效樣本、覆核候選、挑幀取材、驗證幀、拾取檢查、待重拍），只由上面兩個入口呼叫。補充時先在影格上量既有流程的校準對得出影片倍率，所有量測 ÷ 倍率換回流程尺度。
- **檢查指令**：不載引擎、不開視窗，對一個流程資料夾跑 app 既有的結構檢查。edit-flow 以它通過為完成條件，`assemble`、`insert` 寫完也自己跑一次。
- **交付報告**改成 `交付報告/` 資料夾：總覽加每個頂層區段一份。四份在用流程的舊報告在本階段拆好。
- **`app/CLAUDE.md`** 的執行語意搬進格式規範，原處只留實作指標。

## User Stories

1. 身為使用者，我想要交一支示範影片就拿到一份能直接跑的流程，不用事後手框固定矩形，這樣新流程當天就能用。
2. 身為使用者，我想要影片轉出來的找圖步驟自動帶固定矩形，這樣找圖快、也不會在畫面別處認錯。
3. 身為使用者，我想要固定矩形留足夠的餘裕（每邊外推範本寬高的 50%），這樣視窗大小在支援倍率範圍內變動時，圖還在框裡。
4. 身為使用者，我想要內容每次會變的清單（好友列表、迴圈每輪換一列）的框沿捲動方向拉到畫面兩端，這樣清單捲到哪都找得到。
5. 身為使用者，我想要交付報告列出「同區段有拖曳、但沒宣告捲動軸」的找圖步驟，這樣我可以確認它們是不是其實在捲動清單裡。
6. 身為使用者，我想要框超出畫面時直接裁到畫面邊、不算失敗，這樣貼邊的按鈕不會無故被標待重拍。
7. 身為使用者，我想要忙碌指示、確認圖、等消失的目標也照同一套規則產固定矩形，這樣整份流程的框規則一致。
8. 身為使用者，我想要忙碌檢查只勾在 agent 判斷要勾的步驟（送伺服器的操作、或影片裡之後看得到忙碌指示），工具不亂勾，這樣不會每一步都多等。
9. 身為使用者，我想要交付報告列出「勾了忙碌檢查、但之後影格沒看到忙碌指示」與「沒勾、但之後影格看到了」的步驟，這樣漏勾、多勾我都看得到。
10. 身為使用者，我想要勾了忙碌檢查卻沒設忙碌指示時工具直接報錯，這樣不會產出執行時才出錯的流程。
11. 身為使用者，我想要新流程的計畫沒有校準對、或影格上量不到時工具直接報錯，這樣不會拿到跑不動的流程。
12. 身為使用者，我想要範本在影格上不唯一（同一個框裡匹配到多個）時被標成待重拍、列在報告裡，這樣我知道哪幾張要在 app 重截。
13. 身為使用者，我想要待重拍不會讓工具自作主張縮框或改圖，這樣流程照樣寫出來，由我決定怎麼處理。
14. 身為使用者，我想要計畫裡出現已退場的寫法（按鍵、原點矩形、出現等候上限、舊鍵名）時工具報錯並說明，這樣 agent 不會悄悄產出舊格式。
15. 身為使用者，我想要影片裡無法用點擊解釋的畫面變化在報告裡註明「流程不支援按鍵，請改用點擊」，這樣我知道那段要怎麼補。
16. 身為使用者，我想要可選彈窗照舊寫成一個分支的分岔（開頭找圖找不到就跳過、分支內失敗就跳出），這樣跟四份在用流程的寫法一致。
17. 身為使用者，我想要只錄一小段影片（例 add5）就能插進既有流程的指定位置，不用請 agent 手寫一次性腳本，這樣補一段操作很快。
18. 身為使用者，我想要補充時工具在影格上量既有流程的校準對、算出影片倍率，所有座標、拖曳距離、固定矩形與新範本都換回流程尺度，這樣錄影時視窗大小不必跟建流程時一樣。
19. 身為使用者，我想要影片倍率超出支援範圍時工具報錯，這樣不會插進一段尺度錯得離譜的步驟。
20. 身為使用者，我想要影片裡完全量不到校準對時，可以另給一張同取景的圖片讓工具量倍率，這樣錄影時沒拍到標題列也救得回來。
21. 身為使用者，我想要沒有那張圖片時工具拒絕插入，而不是收一個我手打的倍率，這樣倍率永遠是量出來的。
22. 身為使用者，我想要插入點用「第 N 步之後」或「區段 N 裡最前面」指定，並附上第 N 步的內容讓工具核對，這樣編號寫錯時工具會擋，不會插錯地方。
23. 身為使用者，我想要插入段的第一個座標點擊或拖曳之前段內一定有找圖步驟，這樣插入段不會沿用插入點前面某個不相干的原點。
24. 身為使用者，我想要插入後，插入點後面的舊步驟在重新找圖之前用到的原點來源不變，變了就報錯，這樣補一段不會讓後面原本好好的步驟點歪。
25. 身為使用者，我想要插入段可以直接引用既有範本（不重裁），新裁的範本跟既有的撞名時報錯，這樣不會蓋掉在用的圖。
26. 身為使用者，我想要新範本跟某張既有範本幾乎一樣時，報告建議改用既有的，這樣範本不會越積越多重複。
27. 身為使用者，我想要補充沿用既有流程的忙碌指示，這樣不必再取材一次。
28. 身為使用者，我想要補充直接改寫既有流程、不另存備份，前提是 agent 先問我 app 有沒有開著這份、有沒有未存改動，這樣資料夾裡不會冒出一堆備份，也不會被舊視窗存檔蓋掉。
29. 身為使用者，我想要補充的說明寫進插入處那個區段的報告與總覽，而不是報告尾巴多一節，這樣報告永遠描述現況。
30. 身為使用者，我想要對 agent 說「第 30 步改成找不到就跳過」「把這三步包成分岔」就能改好，不必開 app 一步步點，這樣小改動很快。
31. 身為使用者，我想要 agent 改流程時絕不寫猜的座標，要像素值時改用找圖、請我錄影或列進待辦，這樣改完的流程不會點到奇怪的地方。
32. 身為使用者，我想要 edit-flow 交付時告訴我改了哪幾步、要在 app 截哪些範本、要在 app 新增或框什麼，並提醒我在 app 重新讀取這份流程，這樣我知道還剩什麼要做。
33. 身為使用者，我想要 agent 改完先跑檢查指令、沒有錯誤才算完成，這樣不會拿到 app 一讀就報錯的流程。
34. 身為 agent，我想要 flow.yaml 只有一份正本，寫明每個鍵、值、沒寫時是什麼、單位，這樣我不必讀 app 的開發文件，也不會照到過期的那份。
35. 身為 agent，我想要格式規範寫清楚執行語意（區段巢狀、分岔怎麼選分支、`on_fail` 三種與跳出跳到哪、找圖三態、生效確認與補做、忙碌檢查怎麼等、原點與更新原點、座標相對誰），這樣我寫的流程照我以為的方式執行。
36. 身為 agent，我想要格式規範附常見寫法（定位找圖接相對座標、可選彈窗分岔、巢狀重複跳出後的動作、忙碌檢查該勾的標準與四份在用流程勾的 21 步例子、固定矩形餘裕、備用校準對），這樣我照例子寫就對。
37. 身為維護者，我想要格式規範的欄位表跟 app 的預設表、讀檔認得的鍵不一致時 pytest 變紅，這樣改了 app 忘了改文件會被擋下。
38. 身為 agent，我想要「有影片」走 video-to-flow 或 edit-flow 加 video-measure、「沒影片」走 edit-flow，兩個入口的描述清楚分流，這樣使用者說一句話我就知道用哪個 skill。
39. 身為 agent，我想要影片特有的知識只在 video-measure 一處，兩個入口都呼叫它，這樣新流程與補充的量法、驗證標準不會各自漂移。
40. 身為 agent，我想要轉換計畫的步驟鍵跟 flow.yaml 一樣，只多影片證據欄位（`frame`、`box`、`present`、`absent`、捲動軸）、位置寫影片像素，這樣我不用記兩套鍵名。
41. 身為 agent，我想要 `plan-format.md` 只寫跟格式規範不同的地方，並指向規範，這樣兩份文件不會互相牴觸。
42. 身為 agent，我想要檢查指令能對任何一個流程資料夾跑（不載引擎、不開視窗），列出鍵與型別錯誤、區段交錯、相對座標前沒有原點、勾了忙碌檢查沒設忙碌指示、引用了但缺圖的範本，這樣我改完能自己驗。
43. 身為 agent，我想要檢查指令有錯時以非零結束並印出每個錯誤的步驟與原因，這樣我能直接照著修。
44. 身為使用者，我想要缺圖在檢查指令裡列成「要在 app 截的範本」，而不是當成壞掉，這樣 edit-flow 新增找圖步驟（圖還沒截）也能交付。
45. 身為 agent，我想要每份流程的交付報告拆成總覽加每個頂層區段一份，這樣我只改某段時只讀那一份。
46. 身為 agent，我想要總覽列出校準對、倍率、來源影片、待重拍與待確認的索引，並連到各區段那份，這樣我一眼知道整份流程的狀況。
47. 身為 agent，我想要報告用內容指稱步驟（範本名、做什麼），不寫死步驟編號，這樣插入一段後報告不會指錯。
48. 身為使用者，我想要四份在用流程的舊報告在本階段拆成新結構、過期內容標出來，這樣之後改流程的 agent 讀到的是現況。
49. 身為開發者，我想要 `app/CLAUDE.md` 只留實作指標（哪個函式負責）與坑，並寫明改讀檔或預設表要同步格式規範，這樣執行語意不會兩份並存。
50. 身為開發者，我想要 app 的區段結構檢查只有一份實作，app 執行前與檢查指令共用，這樣兩邊對「合法流程」的判斷不會分歧。
51. 身為使用者，我想要 video-to-flow 產的資料夾撞名時加序號、既有流程完全不動，這樣重轉一支影片不會蓋掉在用的流程。
52. 身為使用者，我想要任何報錯都在寫檔前發生、失敗時輸出位置不留半成品（補充時既有流程一個位元都不變），這樣出錯時可以放心重來。

## Implementation Decisions

### 子步驟順序

本階段的範圍互相依賴，建議照這個順序做（每步結束測試全綠）：

1. **檢查指令＋結構檢查抽出**：先把區段結構檢查從 App 抽成模組函式，再做檢查指令。後面的 `assemble`、`insert`、edit-flow 都要用它。
2. **格式規範＋對照測試**：寫 `docs/flow-format.md`，把 `app/CLAUDE.md` 的執行語意搬過去；同時上對照 pytest。
3. **計畫改新鍵＋固定矩形＋忙碌檢查＋報錯條件**（04 全部）。
4. **交付報告改資料夾**（工具端）。
5. **補充插入 `insert`**（13 規則 4–10）。
6. **三個 skill**：拆出 video-measure、瘦身 video-to-flow、新寫 edit-flow；改寫 `plan-format.md`。
7. **四份在用流程的報告拆檔**。
8. **驗收**。

### 結構檢查與檢查指令

- App 現有的執行前結構檢查（區段成對、不可交錯、分岔每個分支開頭必須是找圖點擊、「或」必須直接在分岔內）抽成不依賴視窗的模組函式，輸入完整步驟清單，回傳錯誤訊息；App 改呼叫它，行為與訊息不變。
- 檢查指令是 tools 底下的一個小命令列：參數是流程資料夾。它依序只呼叫 app 既有的東西：讀檔（鍵、型別、`format`）、上面那個結構檢查、每個相對座標點擊／拖曳前的原點來源（沒有原點＝錯）、勾了 `busy_check` 但流程沒設 `busy`、引用了但資料夾裡缺圖的範本。
- 輸出分兩類：**錯誤**（流程讀不進來或執行時一定出錯；非零結束）與**缺圖**（列成「要在 app 截的範本」；缺圖本身不算錯，零結束但印出清單）。不載引擎、不開視窗；預設不寫任何檔，只有加 `--normalize` 且沒有錯誤時，才經 app 的讀寫函式把 `flow.yaml` 重寫一次（更新行尾步驟編號與排版）。
- `assemble` 與 `insert` 寫完流程資料夾後，用同一套檢查自己驗一次；有錯誤就當工具的 bug 報出來。

### 格式規範 `docs/flow-format.md`

- 讀者是寫流程的 agent，不是 app 開發者。內容照 10 第 1 點：
  - 欄位表：頂層與各步驟的鍵、值、沒寫＝、單位；範本命名（平面名稱＝檔名、禁用字元）。
  - 執行語意：從 `app/CLAUDE.md`「UI 慣例」搬來。
  - 常見寫法。
- 詞彙引用 `app/CONTEXT.md`，不重定義。
- 欄位表的格式要讓 pytest 機械讀得出來：一張 md 表，欄位至少有「適用步驟」「鍵」「沒寫＝」。對照測試比三件事：每種步驟的鍵集合＝ app 記憶體模型各步驟可帶的鍵；「沒寫＝」＝ app 預設表；頂層鍵＝讀檔認得的頂層鍵。
- 四份在用流程勾 `busy_check` 的 21 步當例子，寫成「哪一步、為什麼勾」，不貼整份 yaml。
- `app/CLAUDE.md`：「UI 慣例」裡的執行語意刪掉，換成一行指向格式規範；留實作指標（哪個函式負責）與坑；加一行「改讀檔或預設表要同步格式規範（測試會擋）」。根目錄 `CLAUDE.md` 不加指標。

### 轉換計畫（新鍵）

- 步驟鍵跟 flow.yaml 一致：開頭鍵即動作（`find_click`、`find`、`wait_gone`、`click`、`drag`、`wait`、`repeat`、`branch`），時間一律秒，`on_fail`、`busy_check`、`update_origin`、`confirm`、`pick`、`color` 等照 02 schema。區段的寫法跟 flow.yaml 相同（巢狀）。
- 跟 flow.yaml 的差異只有：
  - 位置寫影片像素的畫面位置（`at`、`from`、`to`），不寫 `offset`。
  - 不寫 `within`，由工具算；寫了就報錯。
  - 帶影片證據：步驟的 `frame`；範本的 `frame`、`box`、`present`、`absent`、`clean`。
  - 找圖步驟可宣告捲動軸（`scroll: vertical|horizontal`）。
- 頂層：`video`、`name`、`out`、`templates`、`steps`、`calibration`（`pair`、`frame`、`fallback`）、`busy`（範本＋可選比色）、`report`。
- 舊鍵（`type`、`colorCheck`、`onNotFound`、`timeout` 毫秒、`loop_start`、`busyTarget` 等）、按鍵步驟、原點矩形、出現等候上限，一律報錯，訊息指出新鍵或「已退場」。
- 預設值照 app 預設表（`on_fail` 沒寫＝停止、`timeout` 10、`interval` 0.3）；等於預設的不寫出（交給 app 的寫檔）。工具自己不帶預設表。

### 固定矩形（04 規則 1–4）

- 每個找圖步驟用**它自己那一幀上實際挑中的框**算，不用範本取材位置、不取同範本聯集。框每邊外推範本寬高的 50%（＝範本 2 倍寬高、中心不變），座標相對座標基準點、流程尺度。
- 宣告了捲動軸的步驟：該軸拉到影片兩端，另一軸照 50%。
- 超出畫面就裁到影片邊；裁過的那一側餘裕不足不算失敗、不標待重拍。存檔不裁到搜尋範圍（執行時照裁，現行行為）。
- 忙碌指示、確認圖、`wait_gone` 的目標同一套規則。忙碌指示的框用它在證據影格上的位置算。
- 同一區段裡有拖曳、某個找圖步驟又沒宣告捲動軸的，列進報告的「請確認是否在捲動清單裡」。

### 忙碌檢查與校準對（04 規則 5–8）

- 只有計畫寫了 `busy_check: true` 才勾；工具不自動勾。
- 自我驗證兩向只報告、不擋：勾了但之後影格沒看到忙碌指示 → 提醒；沒勾但之後影格看到了 → 列出。「之後影格」是這一步的幀到下一步的幀之間（最後一步看到影片結束）。
- 計畫有 `busy_check: true` 卻沒有 `busy`＝報錯。
- 新流程（`assemble`）的計畫沒有 `calibration`、或影格上量不到主校準對＝報錯、不組裝。備用對量不到只是不帶備用對，照舊寫明在報告。

### 自我驗證與待重拍（04 規則 9）

- 拾取檢查三項都做，判斷只呼叫 app 的拾取檢查模組（縮放餘裕 ×0.85／×1.15、矩形餘裕、唯一）。
- 矩形餘裕照 50% 規則必過，留著當防呆；沒過＝工具 bug，報錯。
- 「唯一」不過＝標待重拍、列進報告；不自動縮框，流程照寫。

### 補充插入 `insert`（13 規則 4–10）

- 命令列多一個子指令 `insert <計畫> <流程資料夾>`。計畫格式同上，另加：
  - `after: N` 或 `into: N`（擇一）：插在第 N 步之後同一層；N 是區段開頭時，插在整個區段結束後。`into` 是插在區段 N 裡最前面。
  - `expect`：第 N 步的開頭鍵＋範本（例 `{find: 标题_办公室}`），工具核對，不符就報錯。
  - 可選 `scale_image`：使用者給的同取景圖片路徑。
  - 不寫 `calibration`、`busy`、`name`、`out`：一律沿用既有流程。
- **影片倍率**：在所需影格上先找既有流程的主校準對、再找備用對，量出倍率 r 與座標基準點在影格上的位置。r 在支援倍率範圍內都收，超出範圍就報錯。全部量不到時改在 `scale_image` 上量；沒有圖片也報錯。
- **換算**：實作上先把用到的影格整張縮放 1/r、以量到的基準點對齊既有流程的座標基準點，之後所有量測（裁新範本、算固定矩形、位置、拾取檢查）都在流程尺度下做，跟 `assemble` 走同一段程式。
- **原點**：插入段第一個座標點擊或拖曳之前，段內必須有找圖步驟，沒有就報錯。寫回前比對插入前後：插入點後面的舊步驟，在自己重新找圖之前若用到原點（相對座標、`confirm: gone`），原點來源不得改變，變了就報錯，工具不自動修。比對用 app 的原點來源推算。
- **範本**：
  - 步驟引用的範本名不在計畫的 `templates` 裡、但在既有流程資料夾裡，就是引用既有範本：不重裁，照跑拾取檢查。
  - 計畫 `templates` 裡的新範本跟既有範本撞名就報錯。
  - 新範本跟某張既有範本幾乎一樣（引擎互相匹配得到），報告建議改用既有的，不擋。
- 插入段本身可含區段。勾了 `busy_check` 但既有流程沒設 `busy` 就報錯。
- **寫回**：經 app 的讀檔讀進既有流程 → 在記憶體插入 → 經 app 的寫檔寫回；新範本加進 `templates/`。任何報錯都在寫檔前；失敗時既有資料夾一個位元都不變。不備份（13 規則 2）。寫回後跑檢查指令。
- 交付報告：插入處所屬那份與總覽更新，說明寫進內容，不加日期分節。

### 交付報告 `交付報告/`（13 規則 11）

- 流程資料夾裡的 `交付報告/`：`總覽.md` 加每個頂層區段一份（檔名規則見[需要你決定的](#需要你決定的)）。app 不讀不寫，存檔也不動它。
- 總覽：校準對與基準距離（補充時另記影片倍率與來源影片）、來源影片、搜尋範圍、忙碌指示、各份報告的連結；待重拍、待確認（捲動、忙碌兩向）與無法用點擊解釋的畫面變化的索引。
- 各份：這段做什麼、怎麼建的、已知風險、這段的待重拍與待確認。用內容指稱步驟（範本名＋動作），不寫步驟編號。
- 刪「口頭補充的按鍵」一節；「無法用點擊解釋的畫面變化」保留，註明「流程不支援按鍵，請改用點擊」。

### 三個 skill 與計畫格式文件

- **video-measure**（新，不自己觸發，description 寫明只由 video-to-flow、edit-flow 呼叫）：錄影要求、掃描、特效／游標樣本、覆核候選、挑幀取材、驗證幀、拾取檢查、待重拍；忙碌檢查該勾的標準指向格式規範。現有 `SKILL.md` 第 1–7 節大多搬過來，與格式規範重複的判斷規則（分岔寫法、定位找圖、比色、挑選語意）改成指向規範。特效樣本與學游標的附件跟著搬。
- **video-to-flow**（瘦身）：新流程入口。前置檢查 → 呼叫 video-measure → 寫計畫（含校準對）→ `assemble` → 讀驗證結果能修就修 → 交付。不帶補充模式。
- **edit-flow**（新）：description 照 10 第 2 點。流程：
  1. 先問 app 是否開著這份且有未存改動，有就請使用者先存或關掉。
  2. 讀 `flow.yaml` 與格式規範，改結構與選項。
  3. 要像素值時，依序：能改成找圖就寫找圖＋新範本名（缺圖 = 要使用者截）；使用者願意錄影 → 呼叫 video-measure → `insert`；都不行 → 不寫那一步，列進交付清單。`within` 不寫（＝整個搜尋範圍），列為建議。
  4. 跑檢查指令，沒有錯誤＝完成。
  5. 交付：改了哪幾步、要截的範本、要在 app 新增或框什麼，並提醒在 app 重新讀取（別用舊視窗存檔）。
  - edit-flow 直接改 `flow.yaml` 文字。改完行尾的自動步驟編號會過期，所以檢查通過後用檢查指令的 `--normalize` 經 app 讀寫一次，讓編號與排版回到標準（這是檢查指令唯一會寫檔的模式）。
- **`plan-format.md`**：改成新鍵，指向格式規範，只寫差異（影片像素位置、不寫 `within`／`offset`、證據欄位、捲動軸、`insert` 的 `after`／`into`／`expect`／`scale_image`）。現有三處跟程式牴觸的寫法刪掉。移到 video-measure 底下。

### 四份在用流程的報告拆檔（13 規則 12）

- 對 `%USERPROFILE%\AutoClick\` 底下四份流程，各把 `交付報告.md` 拆成 `交付報告/`，舊檔處理方式見[需要你決定的](#需要你決定的)。
- 拆的時候對照現在的 `flow.yaml`：報告提到但流程裡已經不存在的範本、步驟、做法，標成過期。
- 一次性工作，由 agent 手做或用 `.scratch` 裡的一次性腳本，不進 tools。拆完請使用者看過一份。

### 驗收

照[階段切法與順序](../project-cleanup/issues/01-phases-and-order.md)第 2 階段（13 規則 13 修訂後）：

- ① 早_簡中複製一份，刪掉手動段（現在的第 124–129 步：找标题_办公室的分岔、拖曳、找标题_回收站、點擊）。走 edit-flow 用 add5 插回去，跟手動版比：
  - 結構相同（步驟種類、區段、範本引用）。
  - 座標差幾像素內。
  - 固定矩形照新規則算，不跟手框的窄帶比，只要求包含挑中的框。
  - 拾取檢查全過。
  - 使用者在遊戲實跑通過。
- ② demo2（早_繁中，164 秒、繁中最大化）走 video-to-flow 獨立重轉：產出只含固定矩形與計畫明寫的忙碌檢查、拾取檢查全過、檢查指令無錯誤。
- 四份在用流程的報告拆好，使用者看過一份沒意見。
- 實跑前照 memory 先確認使用者不在玩遊戲。

## Testing Decisions

- 好的測試只看外部行為：產出的流程資料夾經 app 讀回的記憶體流程、資料夾裡有哪些檔、報告裡有沒有某個項目、命令列的結束碼與訊息。不測內部函式與中間資料。
- **接縫一：組裝 `assemble`**（已有）。合成影片＋計畫 → 流程資料夾，經 app 讀回斷言。要測：
  - 固定矩形＝挑中框外推 50%、裁到影片邊、捲動軸那軸到兩端；忙碌指示與確認圖也有框。
  - `busy_check` 照計畫原樣；兩向的忙碌報告項。
  - 舊鍵、按鍵、`within` 寫在計畫裡就報錯；沒有校準對、量不到、`busy_check` 沒 `busy` 都報錯，而且輸出位置不多任何檔。
  - 不唯一的範本標待重拍、流程照寫。
  - `交付報告/` 有總覽與各區段檔。
  - 前例：現有組裝測試、照 skill 程序走一遍的測試，以及它們用的合成影片產生器。
- **接縫二：補充插入 `insert`**（新）。合成影片用 ×0.9 這類非 1 倍率產生，加一份 tmp_path 裡的既有流程資料夾（經 app 寫檔建立）。要測：
  - 插入後座標、拖曳距離、固定矩形、新範本尺寸都是流程尺度。
  - `after`／`into` 的位置正確、`expect` 不符時報錯。
  - 倍率超範圍報錯；量不到時用 `scale_image`、沒圖就報錯。
  - 段內沒原點報錯；插入改變後面舊步驟原點來源時報錯。
  - 撞名報錯、引用既有範本不重裁。
  - 任何報錯時既有資料夾逐位元不變。
  - 插入處那份報告與總覽有更新。
- **接縫三：檢查指令**（新）。tmp_path 裡手寫的流程資料夾，逐一放進一種錯誤（區段交錯、分支開頭不是找圖點擊、相對座標前沒原點、`busy_check` 沒 `busy`、未知鍵），斷言結束碼與訊息含步驟與原因；缺圖列成清單、結束碼為零；`--normalize` 把手改過、編號過期的檔寫回標準排版，有錯誤時不寫。App 的執行前檢查改呼叫抽出的函式後，現有相關測試照過。
- **接縫四：格式規範對照**（新）。讀 `docs/flow-format.md` 的欄位表，跟 app 預設表、記憶體模型各步驟可帶的鍵、讀檔認得的頂層鍵比對，多、少、預設值不同都失敗，訊息指出是哪一格。
- 三個 skill 與四份報告拆檔不寫單元測試，靠驗收實跑。
- 影片轉流程測試照舊不開視窗，可在一般環境跑；app 端只有結構檢查抽出這一處，用現有測試當回歸網。

## Out of Scope

- UI 變動：步驟編輯器、主視窗、流程設定對話框（UI 瘦身階段）。app 也不偵測外部修改（edit-flow 靠先問使用者）。
- 工具自動判斷要不要勾忙碌檢查、自動縮框、自動修原點來源。
- 按鍵步驟：流程不支援，影片裡的按鍵只在報告裡請使用者改用點擊。
