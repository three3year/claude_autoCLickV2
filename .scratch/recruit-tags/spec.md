# 公開招募標籤辨識(recruit-tags)

Status: ready-for-agent

本輪只做**可行性驗證**:app 外的命令列工具,吃一張公開招募畫面截圖,在五個`標籤格`內辨識`招募標籤`,
再用專案內的`招募池`快照算出`保底組合`印出。不點擊、不動 app、不進打包版。
詞彙見 `app/CONTEXT.md` 的「公開招募」節;grill 的證據與原型在 `.scratch/recruit-tags/prototype/`。

## Problem Statement

使用者每天在明日方舟的公開招募畫面上看到五個`招募標籤`,要自己對照 arkntools 網站
(https://arkntools.app/#/hr)算出哪些標籤組合保底 4★ 以上,再回遊戲勾選。這件事規則固定、每天重複,
是整套日常流程裡還沒自動化的一段。

要自動化,第一關是「程式看得出這五格各是什麼標籤」。本專案沒有文字辨識,只有以`範本`找圖的引擎,
而引擎已知分不開只差一兩個字的中文(例:近衛幹員 vs 狙擊幹員);grill 時用這張截圖的五個真標籤裁切
實測,五者彼此分得開,但區分度全靠粗篩階段,驗證階段對同款文字按鈕幾乎沒鑑別力,且「近衛幹員」範本在
非 1.0 縮放時會誤吃畫面上方的「可獲得的幹員」標題。手上只有一張截圖、只見過五個標籤,其他 24 個
沒有真截圖可裁。

所以要先回答:**用近似遊戲字型自己渲染的 29 張文字範本,在五個標籤格內能不能可靠地分出每格是哪個標籤?**
答案是能,才值得往「勾選、設時限、刷新、換位」的流程設計走;答案是不能,就改為逐步收集真截圖再議。

## Solution

一支放在 `tools/` 下、與`影片轉流程`同紀律的命令列工具(只用引擎公開 API,不經 runner,不是 app 的
第二條辨識路徑)。使用者給它一張繁中招募畫面截圖,它:

1. 從`招募池`快照裡取出 29 個`招募標籤`的字面(台服繁中、國服簡中各一套),用近似遊戲的字型渲染成
   **只含文字、不含底框**的範本,登錄進引擎。
2. 在截圖上算出五個`標籤格`的位置,每格逐一用 29 張範本查詢,取分數最高者為該格的標籤,並記錄次高者與差距。
3. 依**嚴格通過標準**判定:每格只有一張範本過門檻、且本尊與最高他者的粗篩分數差 ≥ 0.1。
4. 用`招募池`快照算出這五個標籤的`保底組合`(4★ 以上;機器人組合另標),連同每格的辨識結果印出,
   也可輸出成 JSON。

另有一個子命令把台服/國服的 gacha_table 與 character_table 抓下來、整理成`招募池`快照存進工具自己的
資料夾;新幹員進池時由使用者說一聲,重跑一次。

可行性驗證本身是一個**驗收步驟**:拿 grill 的真截圖(繁中視窗 ×0.886)與它放大到最大化尺度的版本各跑一次,
兩次都通過嚴格標準才算可行。這個結果寫在票裡,不是單元測試。

## User Stories

1. 身為玩家,我想把一張招募畫面截圖丟給工具,就知道五格各是什麼標籤,這樣我不用自己讀。
2. 身為玩家,我想工具直接印出保底 4★ 以上的標籤組合,這樣我不用再開 arkntools 對照。
3. 身為玩家,我想看到機器人(支援機械)組合被另外標出,這樣我知道這一格要改短時限。
4. 身為玩家,我想看到保底 5★(資深幹員)與 6★(高級資深幹員)的組合被標出等級,這樣我知道該勾哪個。
5. 身為專案維護者,我想知道渲染範本在五格上的辨識有沒有通過嚴格標準,這樣我能決定要不要往流程設計走。
6. 身為專案維護者,我想看到每格的本尊分數、次高他者與差距,這樣不通過時知道差在哪一格、差多少。
7. 身為專案維護者,我想工具只在五個標籤格內找,這樣格外同字的文字(「可獲得的幹員」)不會混進來。
8. 身為專案維護者,我想同一張截圖能以不同尺度(視窗 ×0.886 與最大化)各驗一次,這樣結論涵蓋兩種執行模式。
9. 身為專案維護者,我想範本是從招募池快照的標籤字面渲染出來的,這樣台服與國服各用自己的字面、不手打 29 個詞。
10. 身為專案維護者,我想渲染用的字型、字重、字高記在輸出裡,這樣驗收結果可以重現。
11. 身為專案維護者,我想一個子命令就能把台服(arkntools tw-for-maa)或國服(Kengxxiao zh_CN)的資料表抓下來建成快照,這樣新幹員進池時重跑一次就好。
12. 身為專案維護者,我想快照記下來源、上游更新時間與抓取時間,這樣看得出它多舊。
13. 身為專案維護者,我想建池時招募池裡對不上幹員表的名字會被明確報出來而不是悄悄略過,這樣組合不會算錯。
14. 身為專案維護者,我想辨識與建池都有 Python 入口函式,這樣測試可以像影片轉流程一樣用真引擎與合成輸入打入口。
15. 身為專案維護者,我想工具不進打包版、不改 app,這樣這輪驗證不影響正在實跑的早晚班流程。
16. 身為玩家,我想輸出能存成 JSON,這樣下一階段展開成流程步驟時有現成的格式可接。
17. 身為專案維護者,我想截圖尺寸不是預期比例時工具明確拒絕並說原因,這樣不會在錯的格子位置上得出假結論。

## Implementation Decisions

### 位置與邊界

- 新工具是 `tools/` 下的獨立套件(與`影片轉流程`並列),有自己的 `__main__` 與 CLI;只用引擎公開 API
  (`make_library`、`Engine.register`、`Engine.query`、`load_config`),引擎參數讀 arknights profile 的設定。
  不碰 app、不經 runner、不進打包版(`CONTEXT-MAP.md` 對`影片轉流程`的描述同樣適用)。
- 兩個入口函式:**辨識**(截圖、客戶端、招募池快照、引擎、可選的格子覆寫 → 結果)與**建池**
  (gacha_table 與 character_table 的 JSON、伺服器 → 招募池快照)。抓取資料表的網路動作包在 CLI 子命令裡,
  不在入口函式內。
- 新增 Pillow 作為工具的依賴(放在 `pyproject` 的工具用 optional extra,不加進 app 的依賴)。

### 招募池快照

- 來源:台服 `arkntools/arknights-data-tw-for-maa`(2026-10-08 仍在更新)、國服 `Kengxxiao/ArknightsGameData` 的 zh_CN;
  兩邊都取 `gacha_table.json` 與 `character_table.json`。
- 29 個`招募標籤`取自 gacha_table 的 `gachaTags`(tagId、tagName;含 29 號「元素」),字面就是畫面上的字。
  組合邏輯只認 tagId,字面只用於渲染與顯示,所以兩服共用同一套邏輯。
- 招募池成員取自 gacha_table 的 `recruitDetail`:去掉標記後按行拆,幹員名以「 / 」分隔;以名字到 character_table
  找幹員,取稀有度(`TIER_n` → n)、職業、位置、`tagList`。幹員的標籤集合 = `tagList` + 職業對應的職業標籤 +
  位置對應的位置標籤(職業、位置的英文列舉 → tagId 的對照表寫在工具裡)。
- 名字對不上、或對到的幹員缺欄位時,建池**失敗並列出全部對不上的名字**,不產生快照(grill 時台服 156 個名字
  有 1 個對不上,原因待實作時查)。
- 快照是工具資料夾內的一個 JSON,一服一份,記錄:伺服器、來源網址、上游最後提交時間、抓取時間、標籤表、
  幹員清單。進版控,手動更新。

### 範本渲染

- 字型:優先用本機已有的 Noto Sans TC 可變字型(繁中)與微軟正黑/雅黑作候選;字重、字高、文字顏色(白字)
  與底色(深灰)由工具的渲染設定決定,**渲染設定隨結果一起輸出**。驗收時若要換字重重跑,用 CLI 選項指定,
  不改程式。
- 範本**只含文字**:緊貼字形外框再留少量邊,不含按鈕底框(grill 實測含底框時他者分數最高 0.52、只含文字 0.36)。
- 範本以 1.0 尺度(最大化、1920 寬客戶區)渲染一次;其他尺度交給引擎的 `scale_range` 與 `expected_scale`。
  字高的 1.0 尺度基準由 grill 截圖(×0.886 時文字高約 24–25px)換算。
- 29 張範本在同一個模板庫登錄一次,登錄產物放在工具的暫存目錄(同`影片轉流程`的做法)。

### 標籤格與查詢

- 五個`標籤格`的位置以 1.0 尺度、相對招募視窗的版面模型表示(從 grill 截圖量,寫在工具裡);
  截圖的尺度 = 截圖寬 ÷ 1920,格子座標按尺度換算;可用 CLI 選項整組覆寫。
  截圖長寬比與預期差太多時拒絕(拒絕原因印在 stderr,結束碼 1,同`影片轉流程`)。
- 每格的搜尋區域 = 格子矩形外擴少量邊;對 29 張範本各查一次,`expected_scale` = 截圖尺度;
  每格記錄:每張範本的 `found`、最佳候選的粗篩分數與驗證分數。
- 每格的判定:本尊 = `found` 且分數最高的範本;**嚴格通過** = 該格恰有一張範本 `found`,且本尊的粗篩分數
  減去其他 28 張最佳候選粗篩分數的最大值 ≥ 0.1。整張截圖通過 = 五格都通過。
  有兩張以上 `found` 時該格標「混淆」並列出全部;沒有任何一張 `found` 時標「未辨識」。
- 空格(標籤少於五個的情況目前不存在)不處理;第六格是灰色空位,不在五格之內。

### 保底組合(照 arkntools 的 Hr 計算)

- 以該格辨識出的五個標籤(混淆或未辨識的格子不參與),列舉 1–3 個標籤的所有子集。
- 每個子集的候選幹員 = 招募池中標籤集合包含該子集全部標籤的幹員;子集不含「高級資深幹員」時剔除 6★。
- 最低稀有度只看 3★ 到 5★(1★、2★ 在 9 小時時限下不會出現;6★ 需高資標籤);最低稀有度 ≥ 4 的子集才是`保底組合`,
  其等級 = 該最低稀有度(含高資 → 6、資深 → 5)。
- 去冗餘:若某組合的真子集已達到相同或更高等級,該組合不列。排序:標籤數少者在前,等級高者在前。
- 機器人:子集含「支援機械」且候選含 1★ 時,另列為機器人組合(需 3:50 以下時限),不與 4★ 保底混在一起。
- 每個組合附上候選幹員名單(名字與稀有度),方便人工對照網站。

### 輸出

- stdout 印人看的摘要:五格(標籤、本尊分數、次高他者與差距、通過/混淆/未辨識)、整張是否通過、
  保底組合清單、機器人組合、渲染設定、快照資訊。
- `--json` 寫同樣內容的 JSON,下一階段展開成流程步驟時直接接。

## Testing Decisions

- 好的測試只看外部行為:給一張截圖與一份快照,斷言每格的標籤、通過與否、組合清單;不斷言引擎內部分數的確切值。
- 測試打兩個入口函式,不打 CLI;用 session 共用的真引擎(`tools/tests/conftest.py` 的 `engine` 夾具)與合成輸入,
  比照 `test_vtf_verify.py`。
- 辨識入口的合成輸入:測試用工具自己的渲染器畫一張假招募畫面(深色格子、白字標籤、格外放一段含「幹員」的
  干擾文字),涵蓋:五格全對且通過、某格放非標籤文字 → 未辨識且整張不通過、尺度 0.886 與 1.0 都認得、
  長寬比不對 → 拒絕、格子覆寫生效。
- 保底組合透過辨識入口以迷你快照測(不另開接縫):含高資 6★、資深 5★、單一 4★ 保底、靠 3★ 拉低而不保底、
  機器人另列、冗餘組合不列、兩服字面不同但 tagId 相同結果一致。
- 建池入口以迷你 gacha_table/character_table 片段測:正常建池、名字對不上時失敗並列出名字、職業/位置轉標籤正確、
  快照帶來源與時間。
- 真截圖的可行性驗收不是測試:在票裡記錄兩個尺度的輸出與通過與否。

## Out of Scope

- 任何點擊:勾選標籤、設時限、確認、刷新標籤、換招募位、沒好標籤時隨便招。
- 展開成流程步驟、流程存檔格式變更、app 任何改動、打包版。
- 簡中客戶端的範本與驗收(建池與渲染設計上支援國服,但簡中截圖與驗收等使用者給資料後另開票)。
- 文字辨識(OCR)、自動更新招募池、網站本身的其他功能(幹員頭像、未實裝幹員切換)。
- 渲染通不過時的「逐步收集真截圖」路線——那是下一輪的決定,本輪只回報通過與否。

## Further Notes

- 標籤共 29 個(gachaTags 含「元素」),grill 時說的 28 是舊數字。
- grill 原型數據:真標籤裁切彼此分得開,只含文字裁切的他者粗篩 ≤ 0.36(含底框 ≤ 0.52),本尊 0.85–1.00;
  驗證階段他者相似度 0.85–0.99 全過 0.8,鑑別力全在粗篩。此結論不能外推到只差一字的標籤組合,這正是本輪要驗的。
- arkntools 的 Hr 計算細節(6★ 剔除、計分只看 3★ 以上、保底表取 3★–5★ 且 min ≥ 4、去冗餘)取自其原始碼,
  實作時以原始碼為準再核一次。
- 本機已有字型:NotoSansTC-VF、NotoSansHK-VF、msyh(微軟雅黑)。專案 `.venv` 目前沒有 Pillow。
- **驗收結論(2026-10-10,票 04)**:字面可行但實質不足——只有字級 25、字重 400 兩尺度都過(預設 24/500 在 ×0.886 不過,
  且最大化只用放大圖驗);「X幹員」與近戰位/遠程位兩族連完美範本都會互相過門檻(引擎極限),粗篩最高者則一律是本尊。
