# Spec：基準測試集從在用流程重製

Status: ready-for-agent

專案整理地圖的基準集階段（ADR 0016）。新的`基準測試集`住在 repo 根目錄 `benchmark/`，案例取自四份在用流程現在的範本和示範影片的影格；新集建好、跑到基線之後，同一階段裡一次刪掉引擎的多張圖登錄路徑、整個 `profiles/` 和舊的建構工具。方法的決定與理由在 project-cleanup 票 08（2026-10-20 grilling），詞彙以根目錄 `CONTEXT.md` 為準（「基準測試集」「已知失敗」「預期尺度」）。

## 需要你決定的

### 案例的答案怎麼來、誰審？

決定（2026-10-20）：工具配對＋agent 先審，你看全部卡片。

- 工具配對、agent 先審，你看全部卡片（建議）：約 100 張卡片，約 15 分鐘。
- agent 審，你只看有疑問的：快，但 agent 看錯的會直接進集合。
- 只用你以前判定過的資料：不用再看，但類型偏向線索和商店。

### 新集多大、怎麼分配？

決定（2026-10-20）：照類型配額，約 100 個。

- 照類型配額，約 100 個（建議）：每類 6–12 個，簡中、繁中各半。
- 每張範本至少一個正例，約 300 個：覆蓋最完整，審核約 45 分鐘、repo 多幾十 MB。
- 跟舊集差不多，約 50 個：每類只有幾個，銳度低。

### 縮放案例怎麼做？

決定（2026-10-20）：真實影格合成到支援倍率範圍兩端 ×0.85、×1.15。

### 跑不過的案例怎麼處理？

決定（2026-10-20）：逐個判。影格不乾淨就換幀或刪；真的是引擎弱點就標成已知失敗。基線＝除已知失敗外 100% 命中＋零誤判。

### 基準集要不要像 app 一樣給預期尺度？

決定（2026-10-20）：跟 app 一樣給，案例沒寫就是 1。

### 舊集、profiles/、多張圖登錄路徑什麼時候刪？

決定（2026-10-20）：新集跑到基線後，同一階段一次全刪，刪完再用新集量一次。

## Problem Statement

引擎品質唯一的客觀驗收是基準測試集，但現在這份 52 個案例的集合量的是兩個月前的東西：範本來自舊範本集，跟四份在用流程脫節；38 個是合成畫面；跨集案例靠多張圖登錄的素材。app 一範本一張圖之後，引擎的多張圖登錄路徑只剩這份舊集在走，想刪也刪不掉——刪了就失去量測依據。另外舊集查詢時不給預期尺度，引擎全範圍掃，跟 app 實際的查法不一樣；忙碌指示這種 app 每天都在問的東西，舊集一個案例都沒有。舊集還住在已經退場的 `profiles/` 裡，讀 profile 的設定檔當引擎參數。

## Solution

用四份在用流程現在的範本，到示範影片順序讀出的影格上配對，產生約 100 個照類型配額的新案例，住在 repo 根目錄 `benchmark/`。agent 先逐張審，再產一頁本機 HTML 卡片頁讓使用者全部看過，錯的修掉或刪掉。基準集執行器改成讀 `benchmark/`、只用引擎內建預設、照 app 的查法傳預期尺度，把已知失敗分開報。新集跑到基線（除已知失敗外 100%＋零誤判）後，同一階段刪掉引擎的多張圖登錄路徑、整個 `profiles/`、舊建構工具與綁舊集的測試，刪完再跑一次確認沒有退步。之後改引擎（門檻、模型、刪路徑）前後都手動跑這份集合。

## User Stories

1. 身為使用者，我要基準集量的是四份在用流程現在的範本，這樣量到的命中率就是我每天在跑的東西。
2. 身為使用者，我要案例畫面來自示範影片的真實影格，而不是合成的雜訊背景，這樣量到的是遊戲真實畫面上的表現。
3. 身為使用者，我要每個案例在卡片頁上看得到範本小圖和畫了紅框的畫面，這樣我一眼判斷答案對不對。
4. 身為使用者，我要該找不到的案例在卡片上標「應該沒有」、不畫框，這樣我只要確認畫面裡真的沒有它。
5. 身為使用者，我要 agent 先審過、把有疑問的卡片排在最前面，這樣我把注意力放在最可能錯的地方。
6. 身為使用者，我要只回報錯的卡片編號就好，這樣審核不必另外填表。
7. 身為使用者，我要卡片頁是本機檔案、遊戲畫面不上傳，這樣我不必擔心畫面外流。
8. 身為使用者，我要審核量約 100 張、15 分鐘看得完，這樣我願意每張都看。
9. 身為使用者，我要簡中、繁中兩個客戶端各佔一半，四份流程都分到，這樣兩邊的退步都抓得到。
10. 身為使用者，我要有同款多個的案例（例如商店同款多格），全部都要找到、不能多，這樣挑選規則依賴的全部匹配有被量到。
11. 身為使用者，我要有比色案例（商店售罄、解锁线索灰色、全部收取藍／暗），這樣顏色不同的同形圖不會被當成同一個。
12. 身為使用者，我要有忙碌指示的案例：在場的幀（含疊字、淡入淡出）要找到、剛消失的幀要找不到，這樣忙碌等待不會卡住、也不會提早往下走。
13. 身為使用者，我要有線索背景的案例（線索面板、線索板），這樣花俏背景上的小圖有被量到。
14. 身為使用者，我要有混淆案例（列名互相像、灰色鈕、同形卡），這樣最容易點錯的地方有把關。
15. 身為使用者，我要有縮放到 ×0.85 和 ×1.15 的案例，這樣支援倍率範圍兩端的表現有被量到。
16. 身為使用者，我要負樣本只挑容易誤判的畫面（同畫面的前後狀態、長得像的東西），這樣負樣本真的量得出誤判。
17. 身為使用者，我要有 6–8 個跨影片案例（同一張範本在別天錄的影片找），這樣遊戲畫面細節變了但範本沒重截的情況有被量到。
18. 身為使用者，我要游標碰到答案框的影格一律不收，這樣案例反映 app 實際執行時（游標已移開）的畫面。
19. 身為使用者，我要轉場、模糊、半透明蓋住的影格不收（除非就是拿來當困難負樣本），這樣失敗不是影格髒造成的。
20. 身為使用者，我要幀號只用順序讀的來源，這樣變動幀率的影片不會讓答案對錯幀。
21. 身為使用者，我要基準集查詢時跟 app 一樣給預期尺度，這樣量到的就是 app 真正的查法。
22. 身為使用者，我要縮放案例自己寫明預期尺度，沒寫的就是 1，這樣加案例時不必每個都寫。
23. 身為使用者，我要基準集只用引擎內建預設參數、不另放設定檔，這樣量到的就是 app 出廠的行為。
24. 身為使用者，我要真的是引擎弱點的案例標成已知失敗、寫明原因，這樣弱點留在集合裡、不被藏掉。
25. 身為使用者，我要報表把已知失敗跟其他案例分開列，這樣一眼看得出有沒有真的退步。
26. 身為使用者，我要已知失敗變成通過時報表提示我拿掉標記，這樣引擎變好時標記不會留著過期。
27. 身為使用者，我要除已知失敗外有任何案例沒過時，指令以失敗結束，這樣「有沒有退步」不必自己讀報表數。
28. 身為使用者，我要每個案例記著來源（哪份流程、哪張範本、哪支影片第幾幀、案例類型），這樣流程換了範本時查得到哪些案例受影響。
29. 身為使用者，我要加案例仍然是丟一個資料夾、不改程式，這樣以後遇到新的失敗情境可以直接補。
30. 身為使用者，我要新集是一份快照，流程以後換範本不必跟著換，這樣基準集不會變成要一直維護的負擔。
31. 身為使用者，我要建構案例的腳本是一次性的、放在這個階段的 `.scratch`，這樣 `tools/` 不多一個依賴 repo 外影片的工具。
32. 身為使用者，我要新集跑到基線之後才刪引擎的多張圖登錄路徑，這樣刪之前就有量測依據。
33. 身為使用者，我要刪完多張圖路徑再跑一次新集，這樣確認刪路徑沒有讓引擎退步。
34. 身為使用者，我要整個 `profiles/` 在同一階段消失，這樣退場的 profile 不再留在 repo 裡。
35. 身為使用者，我要刪 `profiles/` 底下沒進版控的本機舊資料前先問我，這樣我有機會留下想要的東西。
36. 身為使用者，我要舊的建構工具和綁舊集的測試一起刪掉或改寫，這樣全套測試不會指向不存在的檔案。
37. 身為使用者，我要基準集維持手動指令、不接進 pytest，這樣平常的全套測試不變慢。
38. 身為使用者，我要引擎文件寫明「改引擎前後必跑基準集」，這樣以後的 agent 改引擎時不會漏跑。
39. 身為使用者，我要基準集指令不帶參數就跑 repo 的 `benchmark/`，這樣不必記路徑。
40. 身為使用者，我要登錄產物的快取不進版控，這樣 repo 只放案例本身。
41. 身為 agent，我要引擎載入範本清單時一個範本只收一張圖、給多張就報錯，這樣不會有人不小心又走回多張圖路徑。
42. 身為 agent，我要引擎參數裡已退場的遮罩策略不再被接受，這樣過期的設定會被發現而不是被默默忽略。
43. 身為使用者，我要 app 在引擎改完後第一次開流程時自動重建一次登錄快取、照常能跑，這樣刪路徑對我是無感的。

## Implementation Decisions

- **案例格式**：沿用一個案例一個資料夾（畫面截圖、範本圖、`expect.yaml`），一律單張範本。`expect.yaml` 原有欄位不變（`expected`、`center`／`centers`、`tolerance`、`color_check`），新增三種：
  - 來源：流程、範本名、影片、幀號、案例類型。只給人看，執行器不讀。
  - `expected_scale`：沒寫＝1.0；縮放案例寫合成倍率（0.85／1.15），答案座標照比例換算。
  - `known_failure`：值是原因文字。有這個欄位的案例是`已知失敗`。
- **基準集執行器**：
  - 對外介面從「給 profile 資料夾」改成「給基準集資料夾」；指令不帶參數時用 repo 根目錄的 `benchmark/`。
  - 引擎參數只用引擎內建預設，不讀任何設定檔。
  - 每個案例查詢時把 `expected_scale` 當預期尺度傳給引擎（沒寫傳 1.0）。
  - 判定規則不變（命中、漏抓、誤判；同款多個要全中且不能多）。
  - 報表：已知失敗分開一區列出；已知失敗這次通過的，標示「可拿掉標記」；總結行分開算「其他案例」與「已知失敗」。
  - 指令結束碼：除已知失敗外全部命中＝成功；否則失敗。
  - 登錄產物快取仍在基準集資料夾底下的 `_` 開頭子資料夾，`.gitignore` 排除。
- **一次性建構腳本**（基準集階段的 `.scratch`，不進 `tools/`）：
  - 讀 `flows/` 四份在用流程的範本、`示範影片`（oCam 資料夾，路徑含中文要用 imdecode），只用順序讀幀。
  - 答案優先取人工判定過的資料：quick-place 線索判定、商店標註與預期挑選、repo 內留下的 demo2／add5 轉換計畫；其餘用現在的範本在影格上配對。
  - 照類型配額挑候選：一般正例、同款多個、比色、忙碌指示（範本＝流程的忙碌指示）、線索背景、混淆、縮放（真實影格 resize 到 ×0.85／×1.15）、易誤判負樣本、跨影片 6–8 個；簡中、繁中各半，總數約 100。
  - 用 quick-place 票留下的游標偵測篩掉游標碰到答案框的幀；轉場、模糊、半透明的幀除了當困難負樣本外不收。
  - 色偏案例不做。
  - 產出候選案例資料夾，加一頁本機 HTML 卡片頁（範本小圖＋影格畫紅框；負樣本不畫框、標「應該沒有」；每張有編號；agent 有疑問的排前面），卡片頁放 scratchpad、不上傳。
- **審核流程**：agent 逐張看過候選，有疑問的排前面 → 使用者看全部卡片、回報錯的編號 → 修正或刪除 → 案例 commit 進 `benchmark/`。
- **建立基線**：用改好的執行器跑新集；沒過的逐個判：影格不乾淨就換幀或刪，引擎弱點就加 `known_failure`。到「除已知失敗外 100%＋零誤判」為止。
- **引擎刪多張圖登錄路徑**（基線之後）：
  - 刪多張圖對齊與穩定度遮罩，遮罩只剩單張梯度啟發式；粗篩、DINOv2 驗證、比色不動。
  - 範本只持有一張圖；載入範本清單與建模板庫只接受「範本名 → 一個圖檔路徑」，給清單就報錯。
  - 引擎參數的遮罩策略鍵退場：內建預設不再有它，呼叫端交付了就報錯。
  - 登錄快取的比對資訊少了遮罩策略，舊快取會失效、重建一次（app 讀取流程時的背景預載會處理）。
- **一次刪除**（同一階段、引擎改完之後）：
  - 整個 `profiles/`：舊基準集、來源素材、設定檔。`profiles/` 裡沒進版控的本機舊資料（舊 profile 的 flows、workspace 等），刪之前先問使用者。
  - 舊的明日方舟基準集建構工具、只測舊多張圖素材的 profile 測試。
  - `.gitignore` 裡 `profiles/` 的規則。
- **綁舊集真實影格的引擎測試改指新集**：同款多個／小圖示不被雜訊峰擠出、比色只剩真正目標這兩組，改用新集裡對應類型的案例；「明日方舟 profile 設定檔有比色門檻」那支刪掉（設定檔不存在了）。
- **刪完重跑**：引擎改完、舊東西刪完，再跑一次新集，結果要跟基線一樣（已知失敗可以變少，不能變多）。
- **文件**：引擎說明與 agent 文件寫明「改引擎（門檻、模型、刪路徑）前後必跑基準集」與指令；README、`app/CLAUDE.md` 裡指向 `profiles/arknights` 的基準集描述改成 `benchmark/`。README 其他過期內容留給文件階段。
- **順序**：執行器改動 → 建構與審核 → 建立基線 → 引擎刪路徑＋測試改指 → 一次刪除 → 重跑確認 → 文件。

## Testing Decisions

- 好的測試只看對外行為：給一個案例資料夾跑出什麼報表、什麼結束碼；給引擎什麼範本清單會被接受或報錯。不測內部函式怎麼拆。
- **接縫一：基準集執行器的對外介面**（跑一個資料夾 → 報表）。沿用現有基準集程式測試的寫法：在暫存資料夾丟合成小案例。要新增的測試：
  - 案例寫了 `expected_scale` 時，引擎收到的預期尺度就是它；沒寫時是 1.0。
  - 已知失敗沒過：不算進「其他案例」的失敗，報表列在已知失敗區，結束碼成功。
  - 已知失敗通過：報表標示可拿掉標記。
  - 非已知失敗的案例沒過：結束碼失敗。
  - 資料夾裡有設定檔也不讀：結果跟只用內建預設一樣。
  - 不帶參數時讀 repo 的 `benchmark/`。
- **接縫二：引擎的公開介面**（載入範本清單＋查詢）。沿用現有引擎測試：
  - 一個範本給多張圖路徑 → 報錯。
  - 引擎參數帶遮罩策略鍵 → 報錯。
  - 單張圖範本照常登錄、查詢（現有遮罩與步行骨架測試裡多張圖的部分刪掉，單張的保留）。
  - 原本用舊集真實影格的同款多個、比色測試改用新集對應案例後仍綠。
- 案例集本身不寫自動測試：正確性靠使用者審卡片＋跑到基線。一次性建構腳本不寫測試。
- 全套測試要綠（app 全套會開 Tk 視窗：照 memory 在隱藏桌面跑，或先確認使用者不在玩遊戲）。
- 最後驗收：新集刪路徑前、後各跑一次，兩次結果一致。

## Out of Scope

- 引擎粗篩方法、OpenCV 依賴、torch／DINOv2 的去留。
- 色偏、亮度的合成案例。
- 把基準集接進 pytest。
- 流程換範本後自動同步案例。
- 把一次性建構腳本做成 `tools/` 常駐工具。
- 舊集 52/52 和新集分數的直接比較。
- README 其他過期內容（文件階段處理）。
- 8 月的 format 2 舊存檔：不轉換，隨 `profiles/` 一起消失（刪前照樣先問）。
