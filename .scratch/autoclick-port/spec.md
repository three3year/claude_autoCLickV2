# Spec:autoClick 應用移植 — 辨識改用主體偵測引擎

Status: ready-for-agent

相關 ADR:0001(引擎/設定檔分離 + 兩階段管線)、0002(autoClick 應用整包移植、辨識全面改用引擎)。

## Problem Statement

使用者長期以外部專案 autoClick(Tkinter 桌面應用)自動化遊戲操作:在畫面中找模板圖並點擊,編排成流程執行。其辨識核心是 OpenCV 模板比對,在畫面變化(縮放、光影、半透明、細粒度混淆)下不夠準也不夠穩——這正是本專案引擎誕生的原因。引擎已達成 bench 38/38,但 autoClick 呼叫端的整合一直是規格預留的「下一步」,尚未發生。使用者要維護兩個專案、忍受舊辨識的漏抓與誤判,而且 autoClick 不在版本控制下、只能在原機使用,難以搬到其他 Windows 機器。

## Solution

把 autoClick 整包搬入本 repo 成為應用層(`app/`),辨識全面改走本專案的兩階段引擎(粗篩 + 深度驗證),舊比對移除。應用照舊提供:截圖建模板、流程編輯、找圖點擊、掃描範圍、比對測試、F12 急停、迷你狀態視窗;新增 profile 切換與建立(每個遊戲設定檔自帶模板庫、流程存檔與 config)。舊 flow 檔與 flow pack 可單向匯入。以 PyInstaller onedir 打包(torch CPU + DINOv2 權重隨包),在無 Python、無網路的乾淨 Windows 機器上雙擊即用。舊專案並行保留一段時間作後援,不再更新。

## User Stories

1. 身為自動化流程使用者,我想要找圖步驟改用兩階段引擎(粗篩+驗證)辨識,以便在畫面縮放、光影變化、半透明元素與細粒度混淆下仍然準確命中。
2. 身為自動化流程使用者,我想要漏抓與誤判同等地被抑制(引擎的既有紀律),以便流程不會點錯位置或卡在找不到圖。
3. 身為自動化流程使用者,我想要沿用既有的流程編輯體驗(新增/編輯/排序/複製/摺疊步驟),以便不用重新學習操作。
4. 身為自動化流程使用者,我想要 click/drag/wait/key/find_click/loop/branch 全部步驟型別照舊可用,以便既有流程邏輯不變。
5. 身為自動化流程使用者,我想要 find_click 的 timeout/interval/offset/onNotFound/confirm 語意照舊,以便匯入的舊流程行為可預期。
6. 身為自動化流程使用者,我想要 wait_gone 與 confirm=gone/appear 以引擎的 found 判定為準,以便「消失/出現」的判斷與找圖同樣可靠。
7. 身為自動化流程使用者,我想要 branch 分支輪詢照舊(先命中者贏),以便多路徑流程繼續運作。
8. 身為自動化流程使用者,我想要匹配門檻由 profile config 統一管理(match/verify 兩關),以便按「基準測試集總體成績」的紀律調參,而不是每步亂調。
9. 身為自動化流程使用者,我想要步驟編輯器不再出現每步 threshold 欄位,以便介面反映新的門檻語意。
10. 身為自動化流程使用者,我想要用截圖框選(視窗吸附、自訂矩形、放大鏡)建立新模板,以便快速擴充模板庫。
11. 身為自動化流程使用者,我想要 GUI 截圖存成單檔模板後由引擎自動登錄,以便新模板立即可用、不需手動登錄步驟。
12. 身為自動化流程使用者,我想要手動把多張截圖放進同名模板目錄後,引擎自動重新登錄成多截圖模板,以便獲得更好的遮罩品質。
13. 身為自動化流程使用者,我想要「立即比對測試」顯示引擎的查詢結果(框選位置與分數),以便建模板或除錯時確認辨識狀況。
14. 身為自動化流程使用者,我想要模板瀏覽器(資料夾樹、擷取/上傳/改名/刪除/複製/測試)照舊運作並支援多截圖模板目錄,以便管理 profile 的模板庫。
15. 身為自動化流程使用者,我想要設定全域掃描範圍後所有找圖與比對測試只在範圍內搜尋,以便加速辨識並避開畫面雜訊。
16. 身為自動化流程使用者,我想要在 UI 切換 game profile,以便在不同遊戲(或同遊戲不同設定)之間快速轉換。
17. 身為自動化流程使用者,我想要在 UI 建立新 profile(自動建目錄結構並帶入預設 config),以便新遊戲上手不需要手動建檔。
18. 身為自動化流程使用者,我想要每個 profile 自帶 flows 清單,切換 profile 同時切換流程清單,以便模板引用永遠對得上。
19. 身為自動化流程使用者,我想要現有的 arknights profile(模板庫已是多截圖重組版)開箱即用,以便移植後立刻能跑實戰流程。
20. 身為自動化流程使用者,我想要直接匯入舊 flow JSON 檔,以便沿用既有流程而不用重建(其中一個有 175 步)。
21. 身為自動化流程使用者,我想要匯入 .autoclickpack(zip 內含 flow 與模板圖),模板名自動去副檔名對應、缺少的模板圖自動補進 profile,以便舊資產一鍵遷移。
22. 身為自動化流程使用者,我想要匯入時舊的每步 threshold 欄位被安靜丟棄,以便舊檔不因語意不合而匯入失敗。
23. 身為自動化流程使用者,我想要匯出 flow pack(flow + 引用的模板,含多截圖模板目錄),以便把流程搬到其他機器。
24. 身為自動化流程使用者,我想要 F12 隨時全域急停,以便自動化失控時立即拿回控制權。
25. 身為自動化流程使用者,我想要執行時主視窗隱藏、迷你置頂視窗顯示進度與最新日誌,以便監看執行狀態又不遮擋遊戲畫面。
26. 身為自動化流程使用者,我想要執行日誌(等級著色、上限裁切)照舊,以便追蹤每一步的執行結果。
27. 身為自動化流程使用者,我想要「避開游標」照舊(截圖前把游標停到最遠角落),以便 hover 高亮不干擾辨識。
28. 身為自動化流程使用者,我想要執行次數/直到停止、開始延遲等執行控制照舊,以便沿用既有的操作習慣。
29. 身為自動化流程使用者,我想要多螢幕(虛擬桌面、負座標)與 DPI 感知照舊,以便在多螢幕環境正常取圖與點擊。
30. 身為自動化流程使用者,我想要 PyInstaller onedir 打包(含 torch CPU 與 DINOv2 權重),以便在沒有 Python、沒有網路的乾淨 Windows 機器上雙擊即用。
31. 身為自動化流程使用者,我想要打包版沿用系統管理員權限啟動(UIPI 限制),以便對較高權限視窗的點擊不被系統丟棄。
32. 身為自動化流程使用者,我想要引擎驗證模型載入失敗時降級為 coarse-only 並明確警告,以便環境異常時仍可用、且我知道精度變低了。
33. 身為自動化流程使用者,我想要首次啟動時模板自動登錄(免網路),以便部署到新機器不需要額外步驟。
34. 身為維護者,我想要應用內「引擎」一詞專指主體偵測引擎、自動化子系統改名 automation,以便詞彙不撐混。
35. 身為維護者,我想要舊專案的非並行測試(runner 行為、座標空間、區段語意、UI 純邏輯)全數移植且綠,以便移植的行為保真有驗收依據。
36. 身為維護者,我想要引擎 bench 維持 38/38,以便確認整合過程沒有動到引擎行為。

## Implementation Decisions

- **佈局**:應用整包搬入頂層 `app/`(GUI、對話框、覆蓋層、主題、tests),其內部自動化子套件命名 `automation`(runner、win、capture、imgio、flowfmt、hotkey、stage)。引擎維持 `src/subject_detection` 不動。「引擎」一詞在本 repo 專指主體偵測引擎(見 ADR 0002)。
- **移植策略**:整包搬移再改造——原始碼與測試照搬,只動辨識接縫與被移除的功能,行為保真優先於重構。
- **辨識接縫**:runner 原本「grab 螢幕 → find_template(screen, tmpl, threshold)」改為「grab 掃描範圍 → engine.query(profile, template_name, search_region_bgr) → QueryResult」。座標換算照舊:查詢回傳的是搜尋區域內座標,runner 加上截圖原點得到螢幕座標。舊 matcher 模組整個移除,不留備援路徑。
- **引擎生命週期**:應用啟動時建立一次 Engine(驗證模型常駐);切換 profile 呼叫 load_profile(自動登錄/失效重登錄)。模型載入失敗時降級 coarse-only 並在 UI 明確警告。
- **門檻語意**:匹配門檻一律來自 profile config(match_threshold / verify_threshold);步驟資料與編輯 UI 移除 threshold 欄位。匯入舊 flow 時丟棄該欄位,不做分數換算(CCOEFF 與驗證餘弦無可靠對應)。
- **Profile 結構**:`profiles/<game>/` 含 `templates/`(模板庫,單檔或多截圖目錄)、`flows/`(該 profile 的流程存檔)、`config.yaml`、`registered/`(登錄產物,可重建、不進版控)。應用一次連一個 profile;UI 提供切換與建立(建立=建目錄結構+複製預設 config);改名/刪除交給檔案總管。
- **模板管理**:GUI 截圖存單檔模板(v1);多截圖登錄靠手動把檔案整理成目錄,load_profile 自動重登錄。預期座標(_meta.json 的 pos)等呼叫端知識照舊留在應用層,引擎不讀。
- **匯入(單向)**:支援舊 flow JSON 與 .autoclickpack。模板引用「去 .png 副檔名」對應(實戰 flow 只用 cn/、zh/ 前綴,已驗證);pack 內 profile 缺少的模板圖補進模板庫;legacy 螢幕空間座標沿用既有的座標空間遷移邏輯轉為區域空間。匯入後以新格式存入當前 profile 的 flows。不維持雙向相容,舊應用不需要讀新檔。
- **匯出**:flow pack 格式延伸以支援多截圖模板目錄,維持自包自足(flow + 引用模板)。
- **執行環境**:Windows 專用照舊(SendInput 點擊、pynput 鍵盤與 F12、mss 截圖、DPI 感知、虛擬桌面多螢幕)。部署後使用者資料(profiles 含 flows)放在 exe 旁,原始碼執行時用 repo 內目錄(沿用 frozen 切換慣例)。
- **打包**:PyInstaller onedir、--uac-admin 照舊;torch CPU 版與 DINOv2 權重一併打包,目標機免網路免 Python;接受 GB 級體積與單次查詢 ~385ms(準確優先,速度優化留待實測證明太慢再開票)。
- **保留但不啟用**:runner 的 stage 接縫(acquire/release)照搬含測試;ParallelRun 與並行 UI 不移植(原實作有 bug、測試不全,留待日後重做)。
- **移除**:旋轉比對與旋轉模板工具、flood-fill 去背工具(登錄遮罩已涵蓋其目的)、翻新解析度工具(引擎多尺度已涵蓋模板端)、每步 threshold、並行執行 UI。

## Testing Decisions

- **原則**:只測外部行為,不測實作細節——沿用兩邊專案共同的既有紀律(引擎側:只經 load_profile+query 斷言,不碰遮罩內容;應用側:harness 造假件、斷言步驟執行效果與座標,不碰內部狀態)。
- **唯一假件點 = runner 的偵測查詢接縫**。舊 harness 在 find_template/grab/時鐘上造假件並提供 `vision.plan(名稱, [第N次才命中])` 排程;移植後假件形狀改為引擎的 query(回 QueryResult),排程機制與虛擬時鐘原樣保留。runner 的全部行為測試(步驟語意、座標空間、區段/迴圈/分支、stage 接縫)都經這一個接縫驗。
- **引擎不加新測試**:它有自己的測試網與 bench;整合驗收只要求 bench 38/38 維持不增。
- **匯入與 profile 管理用暫存目錄真測**:匯入是資料進資料出(舊 JSON/pack → 新 flow + 模板補檔),profile 列舉/建立/切換直接對暫存目錄操作,不需要 mock。
- **UI 照舊只測純邏輯**(如調色盤),不為 GUI 新增接縫;headless 技巧沿用舊專案文件所載。
- **先行藝術**:舊專案 tests/(runner 步驟、座標空間、區段、origin、stage、UI 調色盤)與其 harness;本專案 tests/(合成 profile 建構器、session 級 engine fixture)。
- **驗收**:非並行舊測試全數移植且綠;引擎 bench 38/38;PyInstaller 包在無 Python、無網路的乾淨機器可啟動。實機 flow 驗證由使用者手動進行,不列自動驗收。

## Out of Scope

- 並行執行(ParallelRun、並行 UI、跨流程分時)——日後重做,本輪只保留 stage 接縫。
- 旋轉比對、去背工具、翻新解析度工具。
- 引擎能力變更(旋轉支援、速度優化、多實例/多模板查詢)。
- 舊應用的任何修改(它並行保留、不再更新)。
- 雙向檔案相容(舊應用讀新格式)。
- GUI 的多截圖登錄操作(「新增截圖到現有模板」留 v2)。
- 跨平台支援(macOS/Linux)。
- 實機遊戲流程的自動化驗收。

## Further Notes

- 模板遷移其實已完成:`profiles/arknights/templates` 就是 autoClick 模板庫的多截圖重組版(autoClick 的 `cn/V.png` + `翻新/cn/V.png` → `cn/V/{cn,翻新}.png`),逐檔對應已驗證。
- 實戰資產:4 個 flow pack(arknightMorning/Night × cn/zh),模板引用只有 cn/、zh/ 前綴——匯入對應規則因此可以很簡單。
- 詞彙對齊(app 落地時處理):engine「模板」vs app「範本」統一;engine「搜尋區域」(查詢輸入的裁切影像)與 app「搜尋範圍/掃描範圍」(使用者設定的螢幕矩形)是兩個不同概念,app 的 CONTEXT.md 搬入後在根目錄建 CONTEXT-MAP.md 區分兩個 context。
- 舊專案的 CLAUDE.md 有大量踩坑紀錄(UIPI、DWM 淡入截圖殘影、headless GUI 測試、中文路徑 imread),移植時應一併帶入 app 層文件。
- 速度背景:挖機流程本有 0.5s 輪詢與大量等待,單次 ~385ms 可接受;branch 多分支輪詢會放大延遲,實測太慢再開優化票。
