# Spec: 圖像主體偵測引擎(Subject Detection Engine)

Status: ready-for-agent

## Problem Statement

使用者在維護遊戲自動化腳本(autoClick)時,需要在螢幕截圖的指定範圍內判斷某個預先準備的目標圖片是否存在並取得位置。既有做法(YOLO、OpenCV 特徵點)命中率不足:模板多為 25–100px 的低紋理 UI 裁切圖,特徵點方法抓不到足夠特徵;部分模板(如線索卡)是半透明元素,拍模板時透出的背景被一起存入,實際畫面上背景卻不同,污染比對;同一元素在不同解析度/介面版本下尺寸不同,目前被迫為每種解析度重抓一整套模板(cn/zh/翻新 三組平行模板集)。漏抓與誤判都會讓自動化腳本卡住或誤操作,兩者都不可接受。

## Solution

建立一個遊戲無關的 Python 偵測引擎,以「登錄 + 查詢」兩個階段運作:

- **登錄(一次性、離線)**:對模板庫中每張模板自動生成有效像素遮罩(排除半透明透出區與可變區、保留主體的穩定結構),並預計算多尺度金字塔與嵌入向量。
- **查詢(<500ms)**:兩階段管線——先在梯度/邊緣域做帶遮罩的多尺度模板匹配粗篩(保召回),再以視覺基礎模型的嵌入相似度驗證候選(保精確),回報存在與否、邊界框座標與分數。

引擎與遊戲設定檔嚴格分離:引擎只實作「怎麼找」,所有遊戲特定知識(模板庫、尺度範圍、閾值、遮罩策略)住在各遊戲的設定檔資料夾。換遊戲=建新設定檔+重跑登錄,引擎零改動。

## User Stories

1. As a 腳本開發者, I want 給定模板名稱與搜尋區域後得到「存在與否 + 邊界框座標」, so that 我的自動化腳本能決定要不要點擊、點在哪裡。
2. As a 腳本開發者, I want 單次查詢在 500ms 內完成(GPU 環境), so that 腳本迴圈不會被判斷拖慢。
3. As a 腳本開發者, I want 引擎對 0.6x–1.5x 的尺度變化與輕微長寬比失真穩定命中, so that 我不必為每種視窗解析度重抓一套模板。
4. As a 腳本開發者, I want 引擎對顏色/亮度差異與色偏穩定, so that 夜間模式、變灰、半透明疊加等狀態不會造成漏抓。
5. As a 腳本開發者, I want 半透明模板(如線索卡)透出的背景被自動忽略, so that 實際畫面背景不同時仍能正確匹配。
6. As a 腳本開發者, I want 模板中會隨遊戲狀態改變的可變區(如「0/7」計數文字)不參與比對, so that 計數變化不會造成漏抓。
7. As a 腳本開發者, I want 小至 20–30px 的低紋理圖示也能辨識, so that 製造站加速、基建鈴鐺這類小按鈕不是盲區。
8. As a 腳本開發者, I want 外觀高度相似的模板(線索 1–7 只差數字與淡標誌)被正確區分, so that 不會把線索 2 誤報成線索 1。
9. As a 腳本開發者, I want 主體不存在時查詢可靠地回報「不存在」, so that 腳本不會在錯的位置誤點。
10. As a 腳本開發者, I want 查詢結果附帶可解釋的分數, so that 我能在呼叫端做額外的信心判斷或記錄。
11. As a 腳本開發者, I want 引擎與模型常駐記憶體、啟動時載入一次, so that 每次查詢不必重新載入模型。
12. As a 腳本開發者, I want 把新裁的模板圖丟進 templates/ 資料夾後重跑腳本就直接可用, so that 累積模板的工作流是「裁圖→丟資料夾→query」,沒有手動登錄步驟。
13. As a 腳本開發者, I want 模板圖片內容變更時(hash 不同)自動重新登錄該模板, so that 我更新模板圖後不會拿到過期的登錄產物。
14. As a 腳本開發者, I want 修改設定檔中影響登錄產物的參數(尺度範圍、遮罩策略)時自動重跑受影響的登錄, so that 我不必記得哪些參數需要重新登錄。
15. As a 腳本開發者, I want 只改 yaml 就能調整門檻與尺度範圍、不碰引擎程式碼, so that 調參不會讓遊戲特定知識滲入引擎。
16. As a 腳本開發者, I want 漏抓時有 debug 輸出顯示粗篩分數與驗證分數, so that 我能判斷該調 match_threshold、verify_threshold 還是 scale_range。
17. As a 腳本開發者, I want 把失敗案例(截圖+模板名+預期結果)存進 benchmark 資料夾, so that 失敗案例累積成回歸測試資產。
18. As a 腳本開發者, I want 一個 bench 工具跑整個基準測試集並回報整體命中率(含漏抓/誤判分項), so that 調參時看整體數字而不是單一案例,避免調參過擬合。
19. As a 未來的新遊戲腳本開發者, I want 建立新的遊戲設定檔資料夾(模板庫+複製預設 config)就能開始使用引擎, so that 支援新遊戲不需要修改引擎程式碼。
20. As a 未來的新遊戲腳本開發者, I want 引擎附一份保守的預設 config, so that 新遊戲能先用預設值跑起來、讓實際失敗告訴我要調哪裡。
21. As a 引擎維護者, I want 引擎可調參數少而可解釋、且全部住在遊戲設定檔, so that 引擎內沒有任何寫死的遊戲特定常數。
22. As a 引擎維護者, I want 明日方舟基準測試集達到 ≥95% 正確(漏抓與誤判都計入), so that 驗收有客觀標準且明確優於舊方法。
23. As a 腳本開發者, I want 搜尋區域由呼叫端指定(接近全螢幕也可), so that 預期座標、語言選擇等遊戲邏輯留在呼叫端,引擎保持無知。
24. As a 腳本開發者, I want 尺度處理做對後 cn 與翻新兩套模板可合併為一套, so that 模板庫維護成本下降。
25. As a 腳本開發者, I want 遮罩生成在只有單張模板時也能運作(退化為梯度穩定度啟發式或整張比對), so that 沒有多組拍攝的新遊戲不被卡住。

## Implementation Decisions

- **引擎/遊戲設定檔分離(架構原則)**:引擎是遊戲無關的 Python 套件;每個遊戲一個設定檔資料夾,內含 `templates/`(模板庫)、`config.yaml`(參數)、`registered/`(登錄產物)、`benchmark/`(基準案例)。判準:「換一個遊戲要不要變」——要變的屬於設定檔,不變的才進引擎。驗收僅以明日方舟設定檔為準,不為尚不存在的遊戲預先投資。
- **公開 API(唯一接縫)**:`Engine()` 建構時載入模型常駐;`load_profile(profile_dir)` 讀取設定與登錄產物並自動補登錄;`query(profile, template_name, search_region)` 回傳 `found: bool`、`box: (x, y, w, h)`、`score: float`。每次查詢針對單一模板、單一搜尋區域。
- **兩階段查詢管線**:(1) 粗篩——梯度/邊緣域的帶遮罩多尺度模板匹配,尺度掃描範圍與長寬比容差來自 config,門檻偏鬆保召回,輸出前幾名候選;(2) 驗證——視覺基礎模型(DINOv2-S 級)嵌入相似度比對候選框與模板主體,門檻偏嚴保精確。梯度域天然抗色偏與亮度差。
- **登錄產物**:每模板的有效像素遮罩、多尺度金字塔、主體嵌入向量。遮罩策略可設定:`multi_capture`(同一元素有多組拍攝時,跨組比對像素穩定度找出主體/可變區)與 `single`(單張模板的梯度穩定度啟發式)。半透明元素與可變文字區由遮罩機制統一處理,引擎內不得出現針對特定模板的特例。
- **自動登錄與失效判斷**:登錄產物記錄模板圖 hash 與 config hash;`load_profile` 發現新模板、模板內容變更、或影響登錄的參數(scale_range、mask_strategy)變更時,自動重跑受影響部分。門檻類參數(match_threshold、verify_threshold)僅查詢時讀取,改動即時生效。
- **config.yaml 參數集(初版)**:`scale_range`、`aspect_jitter`、`match_threshold`、`verify_threshold`、`mask_strategy`。明日方舟初始值:scale_range [0.6, 1.5](由 cn/zh/翻新 三組模板實測)、aspect_jitter 0.1。引擎附保守預設 config 供新遊戲複製。
- **bench 工具**:引擎附帶,輸入設定檔資料夾,跑 `benchmark/` 全部案例,回報整體正確率與漏抓/誤判分項。明日方舟驗收與未來遊戲調參共用同一工具。
- **硬體**:目標環境 Windows + Python + NVIDIA GPU;驗證階段模型須可在 CPU 退化執行(速度不保證),以便無 GPU 環境與 CI 測試。
- **呼叫端邊界**:預期座標(_meta.json)、cn/zh 語言選擇、搜尋區域計算、點擊邏輯全部留在 autoClick 呼叫端;引擎不讀 _meta.json。

## Testing Decisions

- **好測試的定義**:只測外部行為——給定 profile 資料夾與搜尋區域影像,斷言 `query()` 回報的存在與否/座標(容差內)/分數行為。不斷言遮罩內容、金字塔格式、候選清單等內部實作。
- **唯一接縫**:引擎公開 API(`load_profile` + `query`)。登錄與兩階段管線為內部實作,其正確性透過「登錄後查詢的行為」間接驗證;bench 工具是同一接縫的另一個消費者。
- **測試素材**:以真實資料為主——明日方舟三組模板集(cn/zh/翻新)互為測試素材(例如以 cn 模板在翻新版截圖中查詢,驗證尺度不變性);既有失敗案例納入 benchmark;負樣本(主體不存在的截圖)必須涵蓋以驗證誤判防制。
- **可重複性**:測試在 CPU 上可跑(不依賴 GPU);模型與門檻固定時查詢結果須確定性。
- **驗收測試**:bench 工具對明日方舟基準測試集 ≥95% 正確,且單次查詢在 GPU 環境 <500ms(以接近全螢幕的搜尋區域量測)。
- **先例**:全新 repo,無既有測試先例;建立 pytest 慣例。

## Out of Scope

- 多遊戲驗收:架構做分離,但基準測試與參數調校只針對明日方舟。
- 旋轉與部分遮擋:需求已確認不存在。
- 單次查詢同時找多張模板、或回報同一模板的多個匹配位置(單一最佳匹配即可)。
- 自訓單樣本偵測網路(SiamFC 式):列為升級路徑,兩階段管線驗證未達標才考慮。
- autoClick 呼叫端的改寫與整合(引擎完成後另開工作)。
- OCR/文字辨識:計數文字等可變區一律遮罩排除,不辨識其內容。
- 極端長寬比失真(單軸 2x 以上)與 10x 以上縮放。

## Further Notes

- 資料實況(方法選型依據):模板多為 25–100px 低紋理 UI 裁切,最小 26×18;線索卡為半透明元素、模板內含拍攝時透出的背景;cn/zh/翻新三組間實測尺度比約 0.75x–1.3x;`_meta.json` 記錄預期座標,呼叫端可據以縮小搜尋區域。
- 舊方法失敗原因:特徵點在小型低紋理圖上抓不到特徵、半透明模板的背景特徵點污染匹配;通用偵測器對線索 1–7 這種細粒度差異難以區分。
- 調參紀律:遇失敗案例先存入 benchmark 再調參,以整體命中率為準;此工作流寫入使用文件。
- 升級路徑備忘:若兩階段管線未達 95%,以合成資料(主體隨機縮放/色偏/貼隨機背景)訓練 SiamFC 式單樣本偵測網路;訓練資料須刻意多樣化以避免過擬合單一遊戲美術風格。
